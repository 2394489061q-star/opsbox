# opsbox 快速开始

> 本文档解决什么问题：让你在一分钟内把 opsbox 跑起来，看懂它输出的每一列，知道退出码怎么接进 cron 与 CI，并找到该改的那几个阈值在哪儿。关于每个阈值背后的口径，请看 [docs/阈值说明.md](阈值说明.md)；一旦真的出了故障，直接翻 [docs/故障排查手册.md](故障排查手册.md)。

---

## 一、一句话定位

opsbox 是一个 **零第三方依赖的 Linux 服务器巡检与故障排查工具箱**：

- 单文件入口 `opsbox`，纯 Bash（兼容 Bash 3.2+），`lib/` 与 `modules/` 由它 source 加载；
- **全程只读**：不写 `/etc`、不改内核参数、不重启服务，唯一的写入是你在 `-o` 里指定的报告文件；
- 一次执行覆盖 **8 个模块、数十个检查项**，把结论折叠成 `OK / WARN / CRIT / UNKNOWN` 四级，并附上可执行的处置建议；
- 输出 6 种格式，退出码是一份稳定的对外契约，可以直接被 cron、CI、Nagios、Prometheus 消费。

---

## 二、它解决什么问题

运维现场最常见的做法是：登录机器，凭记忆一条条敲 `df -h`、`free -m`、`uptime`、`ss -s`、`systemctl --failed`…… 这套流程有四个绕不开的问题：

| 手工逐条敲命令 | opsbox |
| --- | --- |
| 想起哪条敲哪条，覆盖范围取决于当时的状态和记性，**漏项是必然的** | 每次执行固定覆盖 8 个模块，范围不随人、不随时段变化 |
| inode 耗尽、conntrack 表满、CLOSE_WAIT 堆积、时间漂移这些"平时想不到"的项最容易漏 | 这类高频根因是内置检查项，不需要你临场想起来 |
| 每个人、每台机器的输出格式都不一样，**没法横向比较，也没法纵向对比** | 同一版本输出结构固定，检查项 id 固定，可跨机器、跨时间直接对比 |
| 结论靠人现场判断"这算不算严重"，标准随人漂移 | 阈值集中在配置文件一处，`OK/WARN/CRIT/UNKNOWN` 判定只有一份实现 |
| 想接监控得另写一套采集脚本 | 退出码 + `prom` / `csv` / `json` 输出直接可用 |
| 排查完只有聊天记录，事后复盘无据可查 | `-f md -o` 落盘即可作为工单附件或巡检归档 |

需要说清楚的是：opsbox 的目标是 **把问题快速收敛到"是哪一类问题"**，它不替代 `vmstat`、`iostat`、`dmesg` 这些深挖工具，也不是漏洞扫描器。分工见 [docs/故障排查手册.md](故障排查手册.md) 开头一节。

## 三、30 秒上手

```bash
# 方式一：有仓库地址时
git clone <仓库地址> /opt/opsbox
cd /opt/opsbox

# 方式二：单台救火，直接拷过去（推荐）
scp -r opsbox/ root@10.0.0.12:/opt/

# 只需要给入口加可执行位；lib/ 与 modules/ 是被 source 的，不需要
chmod +x /opt/opsbox/opsbox

# 不带任何参数就是一次全量巡检
/opt/opsbox/opsbox
```

就这三步，没有第四步。三个"不需要"值得强调：

| 不需要 | 说明 |
| --- | --- |
| **不需要安装任何东西** | 只依赖系统自带的 Bash（3.2 及以上）与 `awk`。`ss`、`systemctl`、`journalctl`、`timedatectl`、`ip` 这些命令**有就用、没有就降级**，不会让脚本崩掉 |
| **不需要 root** | 普通用户即可运行。以非 root 运行时，读不了 `/etc/shadow` 之类的检查项会如实给出 `UNKNOWN`，而不是假装通过 |
| **不需要联网** | 全部数据来自本机 `/proc`、`/sys`、`/etc`、`/var/log` 以及本机命令 |

如果是在自己的机器上先"看看效果"，建议先用 `-i 0` 跳过采样等待，几十秒内就能出全量报告：

```bash
./opsbox -i 0          # -i 0 表示不做两次采样，CPU 使用率与磁盘 IO 延迟仅供参考
```

### 关于耗时

默认 `OB_CFG_SAMPLE_INTERVAL=1`。为了让 CPU 使用率和磁盘 IO 延迟这两个"增量型"指标有意义，程序需要**取两次快照并做差**，因此会等待：

- CPU 使用率：等待 1 个采样间隔；
- 磁盘 IO 延迟：再等待 1 个采样间隔。

也就是说默认配置下，磁盘与 CPU 模块各自会 `sleep 1`，总耗时比"纯采集"多约 2 秒。机器上进程数很多时，遍历 `/proc` 还会额外花一点时间。

## 四、输出格式一览

用 `-f/--format` 指定，`md` 与 `markdown` 等价，`prom` 与 `prometheus` 等价。

| 格式 | 适合什么场景 | 形态要点 |
| --- | --- | --- |
| `text`（默认） | 人在终端上看，或者 `ssh` 上去当场排障 | 按模块分组、带 ANSI 颜色、非 OK 项下面缩进一行给出处置建议与阈值 |
| `md` / `markdown` | 归档、周报、工单附件、贴进 Wiki | 含"结论 / 环境概览 / 需要处理的问题 / 完整检查明细"四节，问题项单独成 `###` 小节 |
| `json` | 二次处理、喂给自己写的平台、CI 里做断言 | 带 `schema: opsbox.report/1` 与 `summary.exit_code`，`results` 是扁平数组 |
| `prom` / `prometheus` | 接 Prometheus（node_exporter textfile collector） | 6 个指标，检查项状态以 `opsbox_check_status` 暴露。落地步骤见 [docs/监控接入.md](监控接入.md) |
| `csv` | 丢进 Excel、`awk` 过滤、批量比对 | 表头固定 `status,module,id,title,observed,threshold,advice` |
| `oneline` | cron 邮件主题、只认单行的监控系统、Nagios 插件输出 | 一行内包含状态、主机名、结论、四类计数与时间戳 |

几个约定，写脚本时可以直接依赖：

- **stdout 只有报告本体**，所有提示信息（`[INFO]`、`[WARN]`、`[ERROR]`）一律走 stderr。所以 `./opsbox -f json > report.json` 拿到的永远是干净 JSON；用 `-o` 写文件时 stdout 为空。
- 结果里出现的 `|`、TAB、换行会被扁平成空格，因此按 `|` 切分结果行是安全的（这是内部格式，外部请优先用 `json`/`csv`）。
- 颜色默认在非终端（管道、重定向）下自动关闭；也可以用 `--color` / `--no-color` 强制，或设置环境变量 `NO_COLOR`。

## 五、常规用法

```bash
# 全量巡检，终端报告（默认命令就是 check）
./opsbox

# 只跑磁盘和内存两个模块。注意：-m 是"替换"而不是"追加"
./opsbox -m disk,memory

# 跳过采样等待，快速出结果
./opsbox -i 0

# 生成 Markdown 报告并落盘（目录必须已存在，否则退出码 3）
./opsbox -f md -o /var/log/opsbox/report-$(date +%F).md

# 输出 JSON 给下游程序处理
./opsbox check -f json -o /var/log/opsbox/report.json

# 只关心严重问题：有 CRIT 才返回非零，WARN 不阻断
./opsbox --fail-on crit

# 看看到底有哪些检查项可以精确静音（这是排查时最常用的一条）
./opsbox list

# 看模块清单与中文名
./opsbox modules

# 临时叠加一份配置（最后加载、优先级最高）
./opsbox -c /etc/opsbox/tuning-prod.conf

# 调试：把每条检查项的判定过程打到 stderr
./opsbox -d -m cpu
```

`opsbox list` 会先真正跑一遍采集，然后输出四列：**状态 / 检查项 ID / 说明 / 观测值 | 阈值**。它始终输出这张表格，`-f` 对它不起作用。拿到 id 之后就能精确静音，用法见 [docs/阈值说明.md](阈值说明.md) 的静音一节。

## 六、命令与选项速查

### 命令

| 命令 | 作用 |
| --- | --- |
| `check` | 执行巡检（**缺省命令**，不写就等于 `check`） |
| `list` | 列出本次采集到的所有检查项及其状态，用于拿到精确的静音 id |
| `modules` | 列出可用模块与中文名 |
| `version` | 显示版本（如 `opsbox 1.0.0`） |
| `help` | 显示内置帮助 |

### 选项

| 选项 | 取值 | 默认 | 说明 |
| --- | --- | --- | --- |
| `-f, --format` | `text md json prom csv oneline` | `text` | 输出格式；`markdown`、`prometheus` 是别名 |
| `-o, --output` | 文件路径 | 无（stdout） | 报告写入文件；**父目录必须已存在** |
| `-m, --modules` | 逗号分隔的模块名 | 取配置 | 只运行指定模块，**替换**配置里的模块列表 |
| `-c, --conf` | 文件路径 | 无 | 额外加载一个配置文件，**最后加载、优先级最高**；文件不存在会直接报用法错误 |
| `-i, --interval` | 秒 | `1` | 采样间隔，用于 CPU 使用率与磁盘 IO 延迟；`0` 表示不等待 |
| `--fail-on` | `ok warn crit never` | `warn` | 达到哪个级别才返回非零退出码，语义见下一节 |
| `--no-color` / `--color` | — | 自动 | 关闭 / 强制开启颜色 |
| `-q, --quiet` | — | 关 | 抑制提示信息，只输出报告（`ERROR` 仍会打印） |
| `-d, --debug` | — | 关 | 输出调试日志（含每条检查项的状态） |
| `-h, --help` / `-V, --version` | — | — | 帮助 / 版本 |

模块名固定为这 8 个（**执行顺序取决于配置或 `-m` 的书写顺序**）：

```
system  cpu  memory  disk  network  service  log  security
```

## 七、配置加载顺序

内置默认值 → 依次叠加（**后者覆盖前者**）：

1. `/etc/opsbox/opsbox.conf`
2. `<安装目录>/conf/opsbox.conf`（仓库里自带的带注释模板）
3. `~/.config/opsbox/opsbox.conf`（`HOME` 未设置时按 `/root` 处理）
4. `--conf` 指定的文件

前三个路径**不存在就跳过**，只有 `--conf` 指定的文件不可读会报错（退出码 3）。语法就是普通的 shell 变量赋值，改完立即生效，不需要重启任何东西。

建议做法：**不要直接改仓库里的 `conf/opsbox.conf`**，而是把要覆盖的项写进 `/etc/opsbox/opsbox.conf`。这样升级 opsbox 时你的调优不会被覆盖。例如：

```bash
# /etc/opsbox/opsbox.conf
OB_CFG_DISK_WARN="75"
OB_CFG_DISK_CRIT="85"
OB_CFG_DISABLE_CHECKS="sec.firewall,sec.ip_forward,mem.swap"
```

优先级的一个细节，容易踩坑：

- **`-i/--interval` 命令行参数优先级最高**，它在配置加载完成之后还会再覆盖一次 `OB_CFG_SAMPLE_INTERVAL`。
- `OPSBOX_PROC_ROOT`、`OPSBOX_SAMPLE_INTERVAL`、`OPSBOX_TOP_N` 这类环境变量只是**默认值的来源**，配置文件会覆盖它们。
- 采集根路径的配置项名与对应的环境变量名不同：配置项是 `OB_CFG_PROC_ROOT`，环境变量是 `OPSBOX_PROC_ROOT`。

## 八、退出码语义与 `--fail-on`

退出码是 opsbox 对监控和 CI 的**正式契约**：

| 退出码 | 含义 | 何时出现 |
| --- | --- | --- |
| `0` | 全部通过 | 最坏状态为 `OK`，或被 `--fail-on` 判定为不需要失败 |
| `1` | 存在 WARN | 最坏状态为 `WARN`（默认 `--fail-on warn` 下） |
| `2` | 存在 CRIT | 最坏状态为 `CRIT` |
| `3` | 用法错误 | 未知命令/选项、未知模块、不支持的格式、`--fail-on` 取值非法、`--conf` 文件不可读、`-o` 的输出目录不存在 |
| `4` | 采集失败 | 模块加载失败等内部错误；或最坏状态为 `UNKNOWN` 且 `--fail-on ok` |

### 最坏状态是怎么算出来的

这一点和很多人的直觉不同，值得单独说明：

```
有 CRIT                                  → CRIT
否则 有 WARN                             → WARN
否则 有 UNKNOWN 且一条 OK 都没有          → UNKNOWN
否则                                     → OK
```

也就是说 **`UNKNOWN` 是"兜底"状态：只要还有任何一条检查是 `OK`，整体结论就不会被标成 `UNKNOWN`**。在 `healthy` 测试夹具上运行（`OB_CFG_SAMPLE_INTERVAL=0`）就会看到这种情况：`summary` 里存在若干 `unknown`，而 `summary.status` 依然是 `OK`、`exit_code` 依然是 `0`。这些 `UNKNOWN` 通常来自正常的降级——本机没有 `ip` 命令、没有可读的日志源、`OB_CFG_CRASH_DUMP_DIRS` 指向的目录不存在等等——它们不该把整台机器判成异常。

如果你希望对"采集不到数据"单独告警，请用 Prometheus 侧对 `opsbox_check_status == 3` 做规则，而不是依赖退出码。

### `--fail-on` 的完整真值表

| 最坏状态 | `--fail-on ok` | `--fail-on warn`（默认） | `--fail-on crit` | `--fail-on never` |
| --- | --- | --- | --- | --- |
| `OK` | `0` | `0` | `0` | `0` |
| `WARN` | `1` | `1` | `0` | `0` |
| `CRIT` | `2` | `2` | `2` | `0` |
| `UNKNOWN` | `4` | `0` | `0` | `0` |

几个实践结论：

- 想让流水线"任何警告都拦下来"，用 `--fail-on ok`（任何非 OK 都返回非零）。
- 只想被严重问题叫醒，用 `--fail-on crit`。
- 监控场景（cron + textfile、Nagios 包装脚本）常用 `--fail-on never`，因为此时状态由指标或输出文本表达，退出码反而会引发无意义的 cron 告警邮件。
- 注意 `UNKNOWN` 在默认的 `warn` 与 `crit` 下**都是 `0`**，这是上表里最反直觉的一格。

## 九、接进 cron / CI

### cron

```bash
# /etc/cron.d/opsbox —— 每天 08:00 巡检，只落盘 Markdown，不因 WARN 发邮件
# 注意：cron 表达式里的 % 必须转义成 \%
0 8 * * * root /opt/opsbox/opsbox check -q --fail-on crit \
  -f md -o /var/log/opsbox/$(date +\%F).md
```

要点：

- `-q` 抑制 stderr 上的提示信息，避免给 cron 制造噪音；
- **不要加 `-o`，并且用 `-f oneline`**，让那一行进 stdout——cron 会把 stdout 邮件给 `MAILTO`，`oneline` 天生就是为邮件主题设计的；
- cron 默认 PATH 很短，`ip`、`ss` 这类命令可能找不到，进而让相关检查项变成 `UNKNOWN`。稳妥做法是在 crontab 顶部显式设置 `PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`；
- 直接用 `-o` 写 Prometheus 文本文件不是原子操作，node_exporter 可能读到写了一半的文件，请按 [docs/监控接入.md](监控接入.md) 里的"写临时文件再 mv"方式做。

一个把退出码翻译成"是否打扰人"的最小封装：

```bash
#!/usr/bin/env bash
# /opt/opsbox/bin/opsbox-cron.sh
set -u
OPSBOX=/opt/opsbox/opsbox
LOGDIR=/var/log/opsbox
mkdir -p "$LOGDIR"

report="$LOGDIR/opsbox-$(date +%F).md"
"$OPSBOX" check -q --fail-on warn -f md -o "$report"
rc=$?

case "$rc" in
    0) exit 0 ;;                                  # 一切正常，不打扰
    1|2)                                          # 有 WARN 或 CRIT，发报告
        mail -s "[opsbox] $(hostname) 巡检发现异常（rc=$rc）" ops@example.com < "$report"
        exit "$rc" ;;
    *)                                            # 3/4 是工具自身的问题，必须让人知道
        printf 'opsbox 自身异常退出：rc=%s\n' "$rc" | \
            mail -s "[opsbox] $(hostname) 巡检执行失败（rc=$rc）" ops@example.com
        exit "$rc" ;;
esac
```

注意最后那个 `*` 分支：**退出码 3 和 4 必须单独处理**。把"工具跑挂了"当成"机器没问题"是巡检接入里最危险的一个错误。

### CI

```yaml
# 示例：在构建前跑一遍基线巡检，有 CRIT 就失败
- name: opsbox 基线巡检
  run: |
    chmod +x opsbox
    ./opsbox check -m system,disk,memory,security \
      --fail-on crit -f json -o opsbox-report.json
```

CI 里的三个建议：

1. **用 `-m` 限定模块**。构建容器里通常没有 `systemd`、没有 `journald`、看不到宿主磁盘，全量跑会得到一堆 `UNKNOWN`；限定模块能让结论更有意义。
2. **区分对待 `3` 与 `4`**。多数 CI 只关心非零，但把 `4`（采集失败）当成"检查不通过"会和真实问题混在一起，最好在日志里显式打印退出码。
3. **`--fail-on crit` 通常比 `--fail-on warn` 更合适**，否则一条历史遗留的 WARN（比如 `PermitRootLogin yes`）会让每次构建都红。

## 十、常用调参入口

绝大多数场景只需要动这几项，完整清单与口径解释在 **[docs/阈值说明.md](阈值说明.md)**：

| 配置项 | 默认 | 什么时候要改 |
| --- | --- | --- |
| `OB_CFG_DISABLE_CHECKS` | 空 | 精确静音某些检查项（先用 `opsbox list` 拿到 id） |
| `OB_CFG_DISK_WARN` / `OB_CFG_DISK_CRIT` | 80 / 90 | 日志型或存储型节点想更早预警，收到 75 / 85 |
| `OB_CFG_INODE_WARN` / `OB_CFG_INODE_CRIT` | 80 / 90 | 小文件多的机器（邮件、缓存、镜像层）要重点盯 |
| `OB_CFG_DISK_LAT_WARN` / `OB_CFG_DISK_LAT_CRIT` | 20 / 100 | 机械盘放宽到 50 / 200，本地 NVMe 收到 5 / 20 |
| `OB_CFG_MEM_WARN` / `OB_CFG_MEM_CRIT` | 85 / 95 | 业务本来就大量吃 page cache 时适当放宽 |
| `OB_CFG_LOAD_WARN_MULT` / `OB_CFG_LOAD_CRIT_MULT` | 1.0 / 2.0 | 专用机（数据库）收紧，混部机器放宽 |
| `OB_CFG_SAMPLE_INTERVAL` | 1 | 想更快出结果用 `-i 0`；想更准可以调到 5 |
| `OB_CFG_REQUIRED_UNITS` | 空 | 声明"必须活着"的服务，停了直接 CRIT |
| `OB_CFG_LOG_FILES` | syslog/messages/kern.log | 想把 `auth.log`/`secure` 纳入扫描时（例如查 SSH 爆破） |

## 十一、没有 Linux 环境时怎么验证

整套采集层的根路径都可以注入（`OB_CFG_PROC_ROOT` 等），所以可以在 macOS、Windows 的 Git Bash 或 CI 容器里，用普通目录搭出一台"假服务器"来验证逻辑，不需要 root、不需要虚拟机。

```bash
# 端到端测试套件（语法检查、判定原语、夹具场景、输出格式、退出码契约等 11 组）
bash tests/run-tests.sh

# 保留中间产物（生成的报告与夹具）方便事后翻看
bash tests/run-tests.sh --keep
# 中间产物在 tests/.work/

# 也可以手工生成一套模拟系统，然后自己拿它跑 opsbox
bash tests/fixtures/build.sh /tmp/fake-host healthy     # 健康主机
bash tests/fixtures/build.sh /tmp/fake-host troubled    # 故障主机
```

`tests/fixtures/build.sh` 的用法是 `build.sh <目标目录> [healthy|troubled]`，它会写出一个包含 `/proc`、`/etc`、`/var`、`/run` 以及 `df`、`systemctl`、`journalctl`、`timedatectl`、`ufw` 等 mock 命令的目录树，然后你写一份指向它的配置即可：

```bash
cat > /tmp/fake-host.conf <<'EOF'
OB_CFG_PROC_ROOT="/tmp/fake-host/proc"
OB_CFG_SYS_ROOT="/tmp/fake-host/sys"
OB_CFG_ETC_ROOT="/tmp/fake-host/etc"
OB_CFG_VAR_ROOT="/tmp/fake-host/var"
OB_CFG_RUN_ROOT="/tmp/fake-host/run"
OB_CMD_DF="/tmp/fake-host/bin/df"
OB_CMD_SYSTEMCTL="/tmp/fake-host/bin/systemctl"
OB_CMD_JOURNALCTL="/tmp/fake-host/bin/journalctl"
OB_CMD_TIMEDATECTL="/tmp/fake-host/bin/timedatectl"
OB_CFG_SAMPLE_INTERVAL="0"
OB_CFG_LOG_FILES="/tmp/fake-host/var/log/syslog"
OB_CFG_CRASH_DUMP_DIRS="/tmp/fake-host/var/crash"
EOF

./opsbox check -c /tmp/fake-host.conf
```

**`troubled` 场景有一个必须注意的地方**：它的 `systemctl`、`ufw`、`journalctl` 这三个 mock 是靠一个 marker 文件来切换行为的。不导出下面这个环境变量，它们会表现成"一切正常"，你会以为故障没被检出：

```bash
export OPSBOX_FIXTURE_MARKER=/tmp/fake-host/run/troubled.marker
./opsbox check -c /tmp/fake-host.conf      # 此时才会看到 CRIT 与退出码 2
```

另外：`tests/run-tests.sh` 内部用 `python` 校验 JSON 结构，所以跑测试需要机器上有 `python`；而 **opsbox 本身不依赖 `python`**，也不依赖任何第三方工具。
