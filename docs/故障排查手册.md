# opsbox 故障排查手册

> 本文档解决什么问题：把"服务器不对劲"这个模糊感受，快速收敛到"是哪一类问题"。每一节都按 **现象 → 先用 opsbox 看哪一项 → 输出怎么读 → 再用手工命令下钻 → 常见根因 → 处置** 的顺序展开，命令可以直接复制。阈值与口径的完整说明见 [docs/阈值说明.md](阈值说明.md)。

---

## 使用之前：opsbox 的定位

**opsbox 负责把问题快速定位到"哪一类"，深挖仍然要靠手工命令。**

这句话不是免责声明，而是分工：

- opsbox 是**一次性的快照式巡检**。它能在三十秒内同时看到负载、内存、Swap、脏页、inode、conntrack、连接状态分布、服务状态、日志聚类、安全基线，从而把"机器好像有问题"缩小到"是存储、是内存回收、是连接跟踪表、还是应用没关连接"。
- 它**不是**连续观测工具。`vmstat 1`、`iostat -x 1`、`pidstat`、`sar` 能看到的趋势、尖峰、周期，它看不到。
- 它**不解析**业务日志的语义，只做条数与模板聚类。日志里的根因还得你自己读。
- 它**不读容器 cgroup 限额**、**不做跨机关联**、**不替代漏洞扫描器**。

所以一个典型的使用节奏是：

```bash
# 第一步：用 opsbox 把范围缩小（30 秒）
/opt/opsbox/opsbox -q

# 第二步：根据结论，只针对相关模块再跑一次详细信息
/opt/opsbox/opsbox -m disk,memory

# 第三步：拿着 opsbox 报出来的具体项，用下面的手工命令下钻
```

下文每一节的"先用 opsbox 看哪一项"都给出可直接复制的命令，并且说明**具体该看哪个检查项 id、看到什么值意味着什么**。

## 现象一：机器负载很高，但 CPU 并不高

**这是最常见也最容易被误判的现象**：`uptime` 显示 load 20，`top` 里 CPU 却只有 15%，于是有人开始加 CPU——毫无作用。

### 先用 opsbox 看哪一项

```bash
/opt/opsbox/opsbox -q -m cpu,disk,memory
```

需要重点看的检查项：

| 检查项 id | 看什么 | 结论指向 |
| --- | --- | --- |
| `cpu.load1` / `cpu.load15` | 比值是否 > 1（观测值形如 `比值 2.47 (9.87/4)`） | 确认"负载确实高"，并区分是瞬时还是长期趋势 |
| `cpu.usage` | 是否低（例如 < 30%） | CPU 不是瓶颈 |
| `cpu.iowait` | 是否高（> 10%） | **瓶颈在存储/网络存储**，最大概率指向 |
| `cpu.steal` | 是否 > 0 且持续偏高 | 宿主机超卖，你做什么优化都没用 |
| `mem.dirty` | 是否上千 MB | 脏页回写跟不上，同样是存储问题 |
| `mem.swap` | 使用率是否 > 0 | 换页也会把负载推高 |
| `disk.io_latency` | 是否几十上百 ms | 存储慢的直接证据 |
| `cpu.runqueue` | 是否超过 `2 × 核数` | 就绪队列真的在排队 |

### 输出怎么读

把 `cpu.load1` 和 `cpu.usage`、`cpu.iowait` 三者放一起看，组合有明确含义：

| 组合 | 指向 |
| --- | --- |
| 负载高 + `cpu.usage` 高 + `cpu.iowait` 低 | 真的是算力不足 |
| 负载高 + `cpu.usage` 低 + `cpu.iowait` 高 | **IO 阻塞**，最常见 |
| 负载高 + `cpu.usage` 低 + `cpu.iowait` 也低 + `mem.swap` 高 | 内存回收/换页导致 |
| 负载高 + `cpu.steal` 高 | 云主机被邻居抢占 |
| 负载高 + `mem.dirty` 上千 MB | 脏页回写阻塞 |

**关键机理**：Linux 的运行队列长度包含**不可中断睡眠（D 状态）**的进程。磁盘 IO 卡住时，进程进入 D 状态，负载会涨，但它一次 CPU 都不消耗。这就是"负载高、CPU 低"的根本原因。

### 手工下钻

```bash
# 1) D 状态进程清单 —— 谁被卡住了。这是最关键的一条
ps -eo state,pid,ppid,wchan:25,comm | awk '$1=="D"'

# 2) 全局视角：r（就绪）、b（阻塞）、si/so（换页）
vmstat 1 10

# 3) 块设备视角：%util 是否接近 100、aqu-sz（队列深度）、await、r/s w/s
iostat -x 1 5

# 4) 内核级压力指标（PSI）：io 的 some/full 平均值
cat /proc/pressure/io /proc/pressure/cpu /proc/pressure/memory

# 5) 如果是网络存储，确认挂载与延迟
nfsstat -m 2>/dev/null; mount | grep -E 'nfs|ceph|glusterfs'

# 6) 谁在做 IO
iotop -o -b -n 1 2>/dev/null || pidstat -d 1 5
```

读法要点：

- `vmstat` 的 `b` 列就是 D 状态进程数；`si`/`so` 非零说明正在换页。
- `iostat -x` 看 `%util`（设备繁忙度）和 `aqu-sz`（平均队列长度）。`%util` 接近 100 说明设备已经打满；`await` 高而 `%util` 不高，通常是云盘配额或网络存储的问题。
- `/proc/pressure/io` 里的 `full` 表示**所有**任务都被 IO 卡住的时长占比，比 `some` 更能反映"整机被拖住"。
- `ps` 的 `wchan` 列能直接告诉你内核在哪个函数里等（如 `rwsem_down_read`、`blk_mq_get_tag`、`nfs_wait`）。

### 常见根因

1. **云盘 IOPS/带宽突发额度耗尽**——最常见的云上原因。现象是 `disk.io_latency` 上百 ms、吞吐却不高。
2. **磁盘本身故障或即将故障**——`iostat` 的 `await` 异常高且伴随 `dmesg` 里的 IO 错误。
3. **NFS/Ceph 等网络存储抖动**——D 状态进程的 `wchan` 会显示 `nfs_*`，且 `iostat` 本地盘毫无异常。
4. **脏页回写堵塞**——`mem.dirty` 很高，进程卡在 `balance_dirty_pages`。
5. **内存回收（direct reclaim）**——`mem.available` 很低，进程卡在 `shrink_*`，此时表现为内存问题而非磁盘。
6. **宿主机超卖**——`cpu.steal` 高。

### 处置

| 根因 | 处置 |
| --- | --- |
| 云盘额度耗尽 | 采集 `iostat -x` 与业务延迟的对应证据后向云厂商提工单；短期升配磁盘规格或把热点数据分离到另一块盘 |
| 本地盘故障 | 先备份、再换盘；`smartctl -a` 取证据 |
| 网络存储抖动 | 联系存储侧；本地加缓存层或调大队列；避免把关键路径放在无冗余的网络存储上 |
| 脏页回写堵 | 检查后端写入能力；必要时下调 `vm.dirty_ratio` / `vm.dirty_background_ratio` 让回写更早启动 |
| 内存回收 | 见"现象四"，加内存或修泄漏是根本解 |
| 宿主机超卖 | 提工单或换实例规格，本地优化无效 |

## 现象二：磁盘显示有空间，却写不进去

应用报 `No space left on device`，但 `df -h` 明明还有几十 G。"没空间"在 Linux 上至少有**三种完全不同的原因**，opsbox 能直接区分其中两种。

### 先用 opsbox 看哪一项

```bash
/opt/opsbox/opsbox -q -m disk
```

| 检查项 id | 看什么 | 结论指向 |
| --- | --- | --- |
| `disk.usage.<挂载点>` | 容量使用率（如 `disk.usage.root`） | 容量真的满了 |
| `disk.inode.<挂载点>` | inode 使用率（如 `disk.inode.root`） | **inode 耗尽**：容量充足但建不了新文件 |
| `disk.readonly` | 是否为 CRIT | 文件系统已被挂成只读 |
| `disk.detail.<挂载点>` | 已用/可用/文件系统明细 | 复核对不对得上 |

### 输出怎么读

先把这三个 id 的状态摆在一起：

| `disk.usage.*` | `disk.inode.*` | `disk.readonly` | 指向 |
| --- | --- | --- | --- |
| CRIT（> 90%） | 正常 | OK | 容量确实满了 |
| 正常（如 40%） | **CRIT（> 90%）** | OK | **inode 耗尽**——这就是"有空间却写不进去"的经典答案 |
| 正常 | 正常 | **CRIT** | 文件系统进入只读保护模式 |
| 都正常 | 都正常 | OK | 属于 opsbox 覆盖不到的两类原因，见下 |

### 手工下钻

```bash
# 1) 容量 vs inode —— 永远两条一起看
df -h
df -i

# 2) inode 耗尽时，找出海量小文件躺在哪个目录
find / -xdev -printf '%h\n' 2>/dev/null | sort | uniq -c | sort -rn | head -20

# 3) 容量耗尽时，找出占空间最大的目录
du -x -h --max-depth=1 / 2>/dev/null | sort -h | tail -20

# 4) 已删除但仍被进程持有的文件（df 不减但写不进去的隐形杀手）
lsof -nP +L1 2>/dev/null | head -30

# 5) 是否有配额限制（opsbox 不检查 quota）
repquota -a 2>/dev/null | head -30
xfs_quota -x -c 'report -h' /data 2>/dev/null

# 6) 内核层面的线索
dmesg -T | tail -50
```

### 常见根因

1. **inode 耗尽**：邮件队列、session 文件、容器镜像层、缓存碎片。`df -h` 有空间，`df -i` 已经 100%。
2. **已删除但被进程持有的文件**：日志被 `rm` 了，但写日志的进程没重启，空间不释放。`df -h` 与 `du` 的总和对不上就是这个原因。
3. **配额（quota）打满**：容量和 inode 都没满，但用户/组配额到了。
4. **文件系统进入只读**：见"现象六"。
5. **根分区被 tmpfs/overlay 遮蔽**：往一个被挂载点覆盖的目录里写，实际写到了别的文件系统上。
6. **ext4 保留块**：默认 5% 保留给 root，普通用户实际可用空间比 `df` 显示的要少。

### 处置

| 根因 | 处置 |
| --- | --- |
| inode 耗尽 | 定位小文件目录后**按业务清理**（不要盲目 `rm -rf`）；根治靠调整业务的分文件策略或迁移小文件到独立分区 |
| 已删除未释放 | 找到持有进程（`lsof +L1` 的 PID 列），`systemctl restart <服务>` 或 `kill -HUP` 让进程重新打开日志文件。**注意：重启会让数据丢失的风险窗口出现，别在业务高峰做** |
| 配额打满 | `repquota -a` 找超额主体，清理或上调配额 |
| 只读挂载 | 见"现象六"，**不要**直接 remount,rw |
| 保留块 | 确认可接受后 `tune2fs -m 1 /dev/sdaX`（会降低 root 的应急空间，谨慎） |

> opsbox 能直接区分前三种原因里的前两种（容量/inode）和只读挂载。**已删除未释放和配额问题它不覆盖**，必须用 `lsof +L1` 与 `repquota` 手工确认——这也是本手册反复强调"定位到类别、深挖靠手工"的原因。

## 现象三：服务能 ping 通，但连不上

`ping` 通只证明 ICMP 与三层可达。TCP 连不上属于四层及以上的问题，方向完全不同。

### 先用 opsbox 看哪一项

```bash
/opt/opsbox/opsbox -q -m network,service
```

| 检查项 id | 看什么 | 结论指向 |
| --- | --- | --- |
| `net.conntrack` | 使用率是否 ≥ 80%（尤其 ≥ 95%） | **连接跟踪表满，新连接被直接丢弃**——"能 ping 通但连不上"的头号答案 |
| `net.listen_ports` / `net.listen_count` | 目标端口在不在清单里、监听地址是 `*:port` 还是 `127.0.0.1:port` | 进程没起 / 只监听了本机回环 |
| `net.syn_recv` | 是否 > 50 | 半连接队列堆积（SYN Flood 或 accept 太慢） |
| `net.closewait` | 是否偏高 | 应用没 `close()`，连接池被占满 |
| `net.tcp_total` | 是否接近上限 | 连接数整体打满 |
| `net.default_route` | 是否 CRIT | 没有默认路由，跨网段全不通 |
| `svc.failed.<unit>` / `svc.required.<unit>` | 目标服务是否在失败列表里 | 服务真的挂了或没启动 |

### 输出怎么读

- `net.conntrack` 报 95% 以上，且 `dmesg` 里有 `nf_conntrack: table full, dropping packet`——**结论已定**，这是转发型主机最常见的原因。它的现象特征正是"ping 通（ICMP 走 conntrack 但不占表项）但 TCP 连不上（需要新建表项）"。
- `net.listen_ports` 的观测值形如 `*:22 *:8080`。如果目标端口**根本不在清单里**，那就是进程没监听（没启动、崩了、或监听了别的端口）。如果是 `127.0.0.1:8080` 而不是 `*:8080`，那是**只监听了回环**，外部当然连不上。
- `net.syn_recv` 超过 50 且持续——半连接队列被打满，要么在被 SYN Flood，要么应用 `accept()` 太慢。
- `net.closewait` 高——对端已经发了 FIN，本端应用迟迟不 `close()`，连接被挂住直到耗尽 fd 或连接数上限。

### 手工下钻

```bash
# 1) 目标端口到底有没有在听、监听在哪个地址、哪个进程
ss -lntp | grep -E ':80|:443|:3306'
ss -lntup

# 2) 套接字总览：各状态计数与内存压力
ss -s

# 3) conntrack 现状
sysctl net.netfilter.nf_conntrack_count net.netfilter.nf_conntrack_max
conntrack -C 2>/dev/null   # 需要 conntrack-tools

# 4) 半连接与异常状态
ss -tn state syn-recv
ss -tn state close-wait | head -20

# 5) 内核日志里有没有丢包记录
dmesg -T | grep -iE 'conntrack|table full|nf_conntrack|SYN flood'

# 6) 本机防火墙规则
iptables -S 2>/dev/null | head -30
nft list ruleset 2>/dev/null | head -40

# 7) 从本机直接打一次（绕开部分网络因素）
curl -v --max-time 5 http://127.0.0.1:8080/health
telnet 10.0.0.12 3306
```

### 常见根因

1. **conntrack 表满**（NAT 网关、K8s 节点、Docker 宿主机）。
2. **应用只监听了 `127.0.0.1`**，而调用方从外部访问。
3. **服务根本没起来 / 起来又崩了**——看 `svc.failed.*`。
4. **防火墙 DROP 规则**：注意 DROP 与 REJECT 的表现不同，DROP 会让客户端一直等到超时。
5. **listen backlog 溢出**：`net.syn_recv` 高、`Send-Q` 满。
6. **SELinux 拦截**：`ausearch -m avc -ts recent` 能看到 AVC 拒绝记录。
7. **连接数被占满**：`net.closewait` 堆积或 fd 耗尽（`sys.fd_usage` 高）。

### 处置

| 根因 | 处置 |
| --- | --- |
| conntrack 表满 | 临时调大：`sysctl -w net.netfilter.nf_conntrack_max=1048576`；持久化写入 `/etc/sysctl.d/`。同时按需调大 `nf_conntrack_buckets`（hashsize）与缩短 `nf_conntrack_tcp_timeout_established` |
| 只监听回环 | 改应用配置为 `0.0.0.0` 或指定内网地址；**从安全角度更推荐**绑定具体内网网卡 |
| 服务未运行 | `systemctl status <unit>` + `journalctl -u <unit> -n 100 --no-pager`，修好后 `systemctl reset-failed <unit>` |
| 防火墙 | 只放行必要来源；**不要**为了排障直接 `iptables -F` |
| backlog 溢出 | 调大 `net.core.somaxconn` 与应用自身的 backlog 参数；若疑似攻击则上 SYN cookies 与限速 |
| SELinux | `ausearch -m avc -ts recent` 确认后调整策略或打标签，**不要**简单 `setenforce 0` |

## 现象四：内存看着够，进程却被杀了

`free -m` 显示还有几 G 可用，进程却凭空消失、或者报 `Cannot allocate memory`。这里有**三个不同层面**的内存问题，必须分清。

### 先用 opsbox 看哪一项

```bash
/opt/opsbox/opsbox -q -m memory,system
```

| 检查项 id | 看什么 | 结论指向 |
| --- | --- | --- |
| `sys.oom_events` | 是否 > 0 | **内核确实杀过进程**，最直接的证据 |
| `mem.available` | 是否低于 warn/crit 线 | 可用内存真的枯竭 |
| `mem.used` | 使用率（口径是 `MemTotal - MemAvailable`） | 看整体水位，注意它不是 `free` 的 used 列 |
| `mem.commit` | 是否接近/超过 100% | **内存超售**：物理内存还有空余也会分配失败 |
| `mem.swap` | 使用率 | 换页正在发生 |
| `mem.dirty` | 脏页堆积 | 写回压力，会间接导致内存回收困难 |
| `mem.top` | 占用最高的进程清单 | 直接看到嫌疑人 |
| `sys.kernel_overcommit` | 是否为 2 | 禁止超售，分配会直接失败而不是 OOM |

### 输出怎么读

这三行组合起来就能区分三个层面的问题：

| 观测组合 | 指向 |
| --- | --- |
| `sys.oom_events` > 0 | 内核 OOM Killer 真的动手了。**这是硬证据**，其它都是推测 |
| `sys.oom_events` = 0 但 `mem.commit` ≥ 100% | 不是 OOM，是**地址空间/承诺超限**导致 `malloc` 直接失败 |
| `sys.oom_events` = 0 且 `mem.commit` 正常，但进程被 container runtime 杀掉（退出码 137） | 是 **cgroup 限额**，不是主机内存问题——opsbox 看不到这一层 |
| `mem.used` 高但 `mem.available` 还很大 | 正常的 page cache，**不是问题**，别去"清缓存" |

关于 `mem.used` 的口径要特别注意：它用的是 `(MemTotal - MemAvailable) / MemTotal`，**不是** `free` 的 `used` 列。所以在"缓存型服务"上两者的差距会非常大——opsbox 说 31%，`free` 的 used 口径可能显示 60% 以上。以 opsbox 的口径为准，它已经扣掉了可回收部分。

### 手工下钻

```bash
# 1) 谁被杀了 —— 最重要的一条
dmesg -T | grep -iE 'oom|killed process|out of memory'
journalctl -k --since '24 hours ago' | grep -iE 'oom|killed process'

# 2) 内存全貌（注意 available 而不是 free）
free -m
cat /proc/meminfo | grep -E 'MemTotal|MemAvailable|MemFree|Committed_AS|CommitLimit|Dirty'

# 3) 按进程看实际占用（RSS 排序，比 top 更准）
ps -eo pid,ppid,rss,vsz,comm --sort=-rss | head -20
smem -tk 2>/dev/null | tail -20

# 4) 如果是容器：查 cgroup 限额与统计（opsbox 不覆盖这一层）
cat /sys/fs/cgroup/memory.max 2>/dev/null || cat /sys/fs/cgroup/memory/memory.limit_in_bytes 2>/dev/null
cat /sys/fs/cgroup/memory.events 2>/dev/null    # 看 oom / oom_kill 计数
systemd-cgtop -m -n 1 2>/dev/null | head -20

# 5) 内核超售策略
sysctl vm.overcommit_memory vm.overcommit_ratio vm.swappiness

# 6) 进程退出码线索（137 = 128+9 = SIGKILL，通常来自 OOM）
journalctl -u <unit> -n 50 --no-pager
```

### 常见根因

1. **真的 OOM**：匿名内存（堆、栈）总量超过物理内存 + Swap，内核杀进程。
2. **cgroup 限额**：容器被自己的 `memory.max` 限制，主机看着很空。退出码通常是 137。
3. **承诺超售（commit limit）**：`Committed_AS` 超过 `CommitLimit`，`malloc` 直接返回失败。Java、Redis（`vm.overcommit_memory=2` 时的 fork）、大页分配场景常见。
4. **`vm.overcommit_memory=2`**：禁止超售，内存紧张时 `fork`/`mmap` 直接失败而不是 OOM，报 `Cannot allocate memory`。
5. **内存泄漏**：RSS 随时间单调增长，重启就好、跑一阵又不行。
6. **`free` 的 used 列误判**：其实内存很健康，只是 page cache 多。用 opsbox 的口径或 `MemAvailable` 判断。

### 处置

| 根因 | 处置 |
| --- | --- |
| 真 OOM | 加内存 / 限制单进程内存 / 修泄漏；若允许，配一点 Swap 并设 `vm.swappiness=1` 作为缓冲 |
| cgroup 限额 | 调大容器 `memory.max`；同时检查应用是否按容器限额配置堆大小（JVM 的 `-XX:MaxRAMPercentage`） |
| 承诺超售 | 查 `Committed_AS` 的主要贡献者（JVM 预留、`vm.overcommit_ratio`），调整 `vm.overcommit_memory`/`ratio` 或减少预留 |
| 泄漏 | `pmap -x <pid>`、堆 dump、`smem` 看增长；重启只是止血 |
| 缓存型"假高" | 不需要处置。**不要**执行 `echo 3 > /proc/sys/vm/drop_caches` 当成日常操作 |

## 现象五：应用延迟抖动作数量级

不是"慢了一点"，而是"平时 20ms，突然 2s"，而且会自己恢复。这类问题的特征是**不在 CPU 上**，而在内存回收、存储和网络上。

### 先用 opsbox 看哪一项

```bash
/opt/opsbox/opsbox -q -m memory,cpu,disk,network
```

| 检查项 id | 看什么 | 结论指向 |
| --- | --- | --- |
| `mem.swap` | 使用率是否 > 0 | **Swap 换页**，数量级抖动最经典的原因 |
| `mem.available` | 是否偏低 | 内存回收压力（direct reclaim 会阻塞分配） |
| `mem.dirty` | 是否上千 MB | 脏页回写阻塞写操作 |
| `cpu.iowait` | 是否偏高 | 等 IO |
| `disk.io_latency` / `disk.io_throughput` | 延迟是否几十上百 ms | 存储瓶颈 |
| `net.err_rate.<网卡>` / `net.drop_rate.<网卡>` | 是否非零 | 丢包导致 TCP 重传（重传超时是秒级的） |
| `cpu.steal` | 是否偏高 | 宿主机抢占导致的时间片丢失 |
| `cpu.runqueue` | 是否超过 `2 × 核数` | 排队等待 |

### 输出怎么读

**"数量级"这个量级本身就是线索**：

| 抖动量级 | 最可能的原因 |
| --- | --- |
| 从 ms 级抖到 100ms~1s | 存储 IO 排队、脏页回写阻塞 |
| 从 ms 级抖到 1s~10s | **Swap 换页**、内存直接回收、NFS/云盘超时重试 |
| 从 ms 级抖到几十秒 | TCP 重传超时（丢包）、DNS 超时、连接池耗尽 |
| 周期性（如每小时一次） | 定时任务、日志轮转、备份、监控采集 |

几个具体信号：

- `mem.swap` 只要非零**且**换页在进行（`vmstat` 的 `si`/`so` 非零），就足以解释数量级抖动——换页要走磁盘，比内存慢 5~6 个数量级。
- `net.drop_rate.*` 非零意味着丢包。TCP 一旦丢包，重传超时是按 RTO 指数退避的，体感就是"卡一下"。
- `cpu.steal` 高会让应用的 CPU 时间片被偷走，表现为"没有任何指标异常，但就是偶尔慢"。

### 手工下钻

```bash
# 1) 换页与调度全景（si/so 非零 = 正在换页，这是关键）
vmstat 1 20

# 2) 内存压力（PSI）：full 高说明所有任务都被内存卡住
cat /proc/pressure/memory

# 3) 存储延迟趋势与队列深度
iostat -x 1 10

# 4) 单个连接的 TCP 细节：重传、RTT、cwnd
ss -ti | head -40

# 5) TCP 重传统计
nstat -az 2>/dev/null | grep -iE 'retrans|TcpExtTCPLostRetransmit' | head
netstat -s 2>/dev/null | grep -iE 'retrans|timeout' | head

# 6) 具体是哪个进程在抖（看 D 状态与自愿/非自愿上下文切换）
pidstat -w -u -d 1 10

# 7) 是否有直接的回收阻塞证据
dmesg -T | grep -iE 'reclaim|allocation failure|page allocation stall'
```

### 常见根因

1. **Swap 换页（swap thrashing）**：内存不足或 `vm.swappiness` 偏高。
2. **内存直接回收（direct reclaim）**：`MemAvailable` 偏低时，分配内存的进程要自己去回收，路径上被阻塞。
3. **云盘 IOPS 突发额度耗尽**：前几分钟很快，额度用完就掉到基线，呈现"阶梯式"抖动。
4. **网络丢包 / 网卡队列溢出**：突发流量打满 ring buffer。
5. **脏页回写阻塞**：写入速率长期超过磁盘能力。
6. **宿主机超卖（steal）**。
7. **周期性任务**：备份、`updatedb`、日志轮转、批量任务在同一时刻抢资源。

### 处置

| 根因 | 处置 |
| --- | --- |
| Swap 换页 | 加内存是根本解；数据库类服务把 `vm.swappiness` 设为 1~10；确认没有异常膨胀的进程 |
| direct reclaim | 见"现象四"，降低内存压力 |
| 云盘额度耗尽 | 提工单 + 升配；把大顺序 IO 与随机 IO 分离到不同盘 |
| 丢包 | 调大网卡 ring buffer（`ethtool -G`）、检查交换机端口 CRC；确认不是上层限速 |
| 脏页回写 | 下调 `vm.dirty_background_ratio` / `vm.dirty_ratio` 让回写更早、更平滑地启动 |
| steal | 云厂商工单或换规格 |
| 周期任务 | 错峰调度；把重任务移到低峰期 |

## 现象六：根分区突然变只读

写操作全部失败，`touch /tmp/x` 报 `Read-only file system`。这是**文件系统级别的保护动作**，不是"空间不够"。

### 先用 opsbox 看哪一项

```bash
/opt/opsbox/opsbox -q -m disk,log
```

| 检查项 id | 看什么 | 结论指向 |
| --- | --- | --- |
| `disk.readonly` | 是否 CRIT，观测值会列出具体挂载点 | **直接命中**：确实有挂载点处于 `ro` |
| `disk.usage.<挂载点>` | 容量是否已满 | 空间写满有时会触发某些文件系统的只读保护 |
| `log.errors` / `log.top1` | 是否出现 `EXT4-fs error` / `I/O error` | 文件系统或底层磁盘报错 |
| `disk.io_latency` | 是否异常高 | 底层存储已经不正常 |

### 输出怎么读

- `disk.readonly` 报 CRIT 并列出挂载点，说明 `/proc/mounts` 里该挂载点的选项含 `ro`。**这一步就把问题定性了**：不是权限问题、不是空间问题，是文件系统或磁盘。
- `log.errors` 的聚类结果（`log.top1`）如果第一条就是 `EXT4-fs error` 或 `I/O error`，基本可以确认是磁盘侧故障触发了 `errors=remount-ro`。
- 如果 `disk.readonly` 报出头分区 `/`，同时 `log.errors` 里没有任何 IO 报错，那么可能是**挂载配置**问题或人为操作（例如有人手工 remount）。

> 注意：`disk.readonly` 会把**任何**不在排除规则里的只读挂载都报成 CRIT，包括本来就应该只读的挂载（例如某些发行版的 `/boot`、只读 bind mount）。如果这台机器上有这类正常挂载，请把它们加进 `OB_CFG_DISK_EXCLUDE_MNT`，不要在真正的故障发生时被噪音干扰判断。

### 手工下钻

```bash
# 1) 当前挂载状态，找出所有 ro
mount | grep -E '\bro\b'
cat /proc/mounts | awk '$4 ~ /(^|,)ro(,|$)/ {print $2, $3, $4}'

# 2) 内核报错 —— 最关键的一条
dmesg -T | tail -80
dmesg -T | grep -iE 'ext4|xfs|i/o error|remount|read-only|medium error|sense key'

# 3) 本次启动以来的文件系统相关日志
journalctl -k -b --no-pager | grep -iE 'ext4|xfs|i/o error|ata|nvme|scsi' | tail -50

# 4) 磁盘健康（需要 smartmontools；云盘可能不支持）
smartctl -a /dev/sda 2>/dev/null | grep -iE 'health|reallocated|pending|uncorrect'
smartctl -a /dev/nvme0 2>/dev/null | grep -iE 'critical|media|percentage'

# 5) 该设备是否还在线
lsblk -o NAME,SIZE,TYPE,MOUNTPOINT,RO
cat /sys/block/sda/device/state 2>/dev/null

# 6) 空间是否真的满了（有些文件系统在满时会转只读）
df -h; df -i
```

### 常见根因

1. **磁盘坏道 / 介质错误（medium error）**：`dmesg` 里能看到 `I/O error`、`sense key`、`UNC`。
2. **文件系统元数据损坏**：突然断电、内核崩溃后重启，ext4/xfs 检测到不一致。
3. **写超时（command timeout）**：云盘或存储链路抖动，SCSI 层 abort 后 `errors=remount-ro` 触发。
4. **NFS 断连**：`hard` 挂载的 NFS 服务器不可达时，行为更接近"卡死"而不是只读。
5. **容量写满 + 文件系统策略**：少数文件系统在极端情况下转只读。
6. **人为/自动化误操作**：某个脚本执行了 `mount -o remount,ro`。

### 处置

**顺序非常重要，这是数据安全的关键：**

1. **先确认再动手**。`dmesg -T | tail -80` 看是哪种错误。如果是硬件/介质错误，任何写操作都可能加剧损坏。
2. **立刻做数据备份**。只读状态下数据仍然可读，这是抢救数据的黄金时间：
   ```bash
   rsync -a --info=progress2 / /backup/rootfs-$(date +%F)/ 2>/dev/null
   # 或至少把关键业务数据目录导出去
   ```
3. **不要盲目 `mount -o remount,rw /`**。在硬件故障的情况下，这会让损坏扩散到更多元数据。
4. **如果是云盘**：先在控制台对磁盘做快照，再考虑换盘/迁移。
5. **如果是本地盘且确认是坏道**：更换磁盘并从备份恢复；`fsck` 只能在维护窗口内、且必须**先 umount**（对根分区需要救援模式）：
   ```bash
   # 仅在对数据盘操作、且已 umount 的前提下
   umount /data && fsck -y /dev/sdb1
   ```
6. **如果是人为误操作**：确认没有其它故障后，可以 remount,rw；但请追查是哪个变更/脚本干的。
7. **事后**：把这次事件中 `dmesg` 的完整输出留档——云厂商工单和硬件保修都需要它。

## 现象七：SSH 被暴力破解

`/var/log/auth.log` 里刷满了 `Failed password`，负载偏高，或者更糟——已经被登录成功了。**这个现象的危险程度取决于"是否有 UID 0 后门账户"，opsbox 能直接给你答案。**

### 先用 opsbox 看哪一项

```bash
/opt/opsbox/opsbox -q -m security,network,log
```

| 检查项 id | 看什么 | 危险等级 |
| --- | --- | --- |
| `sec.uid0` | 是否出现除 root 之外的 UID 0 账户 | **最高**——这通常意味着已经被人拿到 root 并留了后门 |
| `sec.empty_passwd` | 是否有空密码账户 | **最高** |
| `sec.ssh_passwordauth` | 是否 `PasswordAuthentication yes` | 高——这是爆破能成功的前提 |
| `sec.ssh_permitroot` | 是否 `PermitRootLogin yes` | 高——爆破目标直接对准最高权限 |
| `sec.firewall` | 是否 inactive | 中——缺少边界限制，爆破流量可以直达 |
| `net.syn_recv` | 是否 > 50 | 中——半连接堆积，可能正在被扫 |
| `net.tcp_total` | 是否偏高 | 中 |
| `sec.mac` | SELinux/AppArmor 状态 | 中——被拿下后缺少第二层防护 |
| `log.errors` / `log.top1` | 是否有高频的认证失败模板 | 低——**默认配置下通常看不到**，见下 |

### 输出怎么读

**按危险程度排序来读**：

1. **`sec.uid0` 是 CRIT** → 立刻当成安全事件处理，不要再纠结"是不是被爆破"，先做隔离和取证。这是典型的权限维持手法。
2. **`sec.empty_passwd` 是 CRIT** → 同上，立即锁定账户。
3. **`sec.ssh_passwordauth` 是 WARN（`PasswordAuthentication yes`）** → 说明爆破有成功可能，应该尽快切换到密钥登录。
4. **`sec.ssh_permitroot` 是 CRIT（`PermitRootLogin yes`）** → 爆破目标收敛到 root，风险最高。
5. **`sec.firewall` 是 WARN** → 若你们依赖云安全组，可静音；否则说明本机没有边界限制。

**关于日志这一项，有一个必须知道的限制**：opsbox 的日志模块在有 journald 的系统上优先使用 `journalctl -p err`，而 SSH 认证失败（`Failed password`）是 **info 级**记录，**不会出现在该窗口里**；退化到文件扫描时，默认的 `OB_CFG_LOG_FILES` 是 `/var/log/syslog /var/log/messages /var/log/kern.log`，**也不包含 `auth.log`/`secure`**。所以"爆破没被 opsbox 报出来"不等于没发生，请务必用手工命令确认。想看的话可以：

```bash
# 把认证日志纳入扫描（Debian/Ubuntu）
# /etc/opsbox/opsbox.conf
# OB_CFG_LOG_FILES="/var/log/syslog /var/log/messages /var/log/kern.log /var/log/auth.log"
```

### 手工下钻

```bash
# 1) 失败次数与来源 Top（最直接的证据）
grep -c 'Failed password' /var/log/auth.log 2>/dev/null
grep 'Failed password' /var/log/auth.log 2>/dev/null | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn | head -20
journalctl -u ssh -u sshd --since '24 hours ago' --no-pager 2>/dev/null | grep -c 'Failed password'

# 2) 是否有成功登录（这一步决定是"被打"还是"已被攻破"）
last -ai | head -30
lastb | head -20            # 失败登录记录
journalctl -u ssh -u sshd --since '7 days ago' --no-pager | grep -i 'accepted' | tail -30
grep 'Accepted' /var/log/auth.log 2>/dev/null | tail -20

# 3) 账户侧排查：有没有被加进来的后门
awk -F: '$3 == 0 {print}' /etc/passwd
awk -F: '$2 == "" {print}' /etc/shadow 2>/dev/null
ls -la /root/.ssh/ /home/*/.ssh/ 2>/dev/null
cat /root/.ssh/authorized_keys 2>/dev/null

# 4) 持久化痕迹
crontab -l 2>/dev/null; ls -la /etc/cron.d/ /etc/cron.daily/ 2>/dev/null
systemctl list-units --type=service --state=running | head -30
ls -la /etc/systemd/system/ | head -30

# 5) 当前连接
ss -tnp state established '( sport = :22 or dport = :22 )'

# 6) 防护是否生效
systemctl status fail2ban 2>/dev/null | head -10
fail2ban-client status sshd 2>/dev/null
```

**关键区分**：`lastb` 有大量失败记录、但 `last` 与 `Accepted` 里**没有**陌生 IP 的成功登录，说明还只是"被打"；一旦出现陌生 IP 的成功登录，或 `/etc/passwd` 里多了 UID 0 账户，性质就变成了"已被入侵"。

### 常见根因

1. **端口 22 暴露在公网**且允许密码登录——这是被爆破的根本前提。
2. **没有 fail2ban 之类的自动封禁**。
3. **root 允许直接登录**，把攻击目标收敛到了最高权限。
4. **弱密码或密码复用**，导致爆破最终成功。
5. **云安全组过于宽松**，任何来源都能访问 22 端口。

### 处置

**如果判定"已被入侵"，处置顺序是"隔离 → 取证 → 重建"，而不是"改密码了事"：**

1. **隔离**：安全组里只放行你的运维 IP，或直接摘除公网。
2. **取证**：把 `/var/log/auth.log`、`last`/`lastb` 输出、`/etc/passwd`、`crontab -l`、`systemctl list-units`、`/root/.ssh/` 全部留档。**在取证完成前不要清日志**。
3. **处置后门**：禁用异常账户（`passwd -l`、`usermod -L`）、删除陌生的 `authorized_keys` 条目、清理恶意 cron 与 systemd unit。
4. **重建**：被拿到 root 的机器**不能保证清理干净**，正规做法是用可信镜像重建并恢复数据。
5. **加固**（无论是否被攻破都该做）：
   - 关闭密码登录：`PasswordAuthentication no` + 密钥认证；
   - `PermitRootLogin prohibit-password`，改用普通用户 + `sudo`；
   - 部署 fail2ban 或云 WAF 做自动封禁；
   - 从安全组限制 22 端口的来源 IP；
   - 保持 `sec.uid0`、`sec.empty_passwd` 这两项在监控里告警——它们是"已经被攻破"的最强信号。

**关于"改 SSH 端口"**：它只能减少扫描噪音，**不是安全措施**（端口扫描几秒钟就能发现）。不要把它当成加固手段。

## 现象八：时间不同步导致证书报错

典型表现是 `curl`/`wget`/应用报 `certificate is not yet valid` 或 `certificate has expired`，而证书本身其实是好的。根因是**本机时钟不在证书的有效期内**。

### 先用 opsbox 看哪一项

```bash
/opt/opsbox/opsbox -q -m system
```

| 检查项 id | 观测值 | 结论指向 |
| --- | --- | --- |
| `sys.time_sync` | `已同步（NTP=yes）` | 本机时钟可信，证书报错要去查证书本身 |
| `sys.time_sync` | `未同步（NTP=no）` | **直接命中**：时钟不可信，证书校验必然受影响 |
| `sys.time_sync` | `无法判定（缺少 timedatectl/chronyc）` | 本机既没有 systemd-timedated 也没有 chrony，必须手工查 |
| `sys.uptime` | 运行时长很短 | 机器刚重启过，时钟可能还没完成同步 |

### 输出怎么读

- `sys.time_sync` 的判定来源依次是：`timedatectl show` 的 `NTPSynchronized` 字段 → `chronyc tracking` → 都没有则给 `UNKNOWN`。
- 看到 `未同步` 时，TLS 报错的原因基本已定：客户端与服务端时间差超过证书有效期边界，就会报 `not yet valid`（客户端慢）或 `expired`（客户端快）。
- 看到 `无法判定` 时**不要**直接认为没问题——最小化容器、精简镜像里经常既没有 systemd 也没有 chrony，而时钟漂移恰恰在这些环境里最常见（尤其是 VM 休眠/恢复之后）。

**注意区分两种情况，别把证书过期误判成时间问题**：

| 情况 | 特征 | 判断方法 |
| --- | --- | --- |
| 本机时钟错 | `date -u` 与真实 UTC 偏差大；`sys.time_sync` 报未同步 | 换一台已知时钟正确的机器对比 |
| 证书真的过期/未生效 | 本机时钟正确，但证书的 `notBefore`/`notAfter` 不包含当前时间 | 手工读证书有效期 |

### 手工下钻

```bash
# 1) 本机时钟与同步状态
date -u
timedatectl status 2>/dev/null
timedatectl timesync-status 2>/dev/null

# 2) chrony 的详细状态：偏移量、是否已同步、上游源是否可达
chronyc tracking 2>/dev/null
chronyc sources -v 2>/dev/null
chronyc sourcestats -v 2>/dev/null

# 3) 若是 systemd-timesyncd
systemctl status systemd-timesyncd --no-pager 2>/dev/null

# 4) NTP 端口是否被挡（UDP 123）
nc -vzu pool.ntp.org 123 2>&1 | head -3
chronyc -n sources -v 2>/dev/null | grep -E '^\^\*|^\^\+|^\^-'

# 5) 证书到底是什么情况
openssl x509 -in /etc/ssl/certs/server.pem -noout -subject -dates
echo | openssl s_client -connect api.example.com:443 -servername api.example.com 2>/dev/null \
  | openssl x509 -noout -dates -subject

# 6) 复现报错，看到底是哪一种
curl -v https://api.example.com/ 2>&1 | grep -iE 'certificate|expire|not yet valid|SSL'

# 7) 硬件时钟与 UTC 的关系
timedatectl | grep -iE 'RTC|Time zone|Local time|Universal time'
hwclock --show 2>/dev/null
```

### 常见根因

1. **chronyd / systemd-timesyncd 没有启用**（尤其是从镜像批量部署的机器）。
2. **UDP 123 被防火墙或安全组挡住**，时钟源根本不可达。
3. **虚拟机休眠/恢复后的时钟跳跃**（VirtualBox、VMware 的宿主时间同步功能与之冲突）。
4. **容器共享宿主时钟**，宿主本身漂移，容器跟着错。
5. **RTC 被设为本地时间**而非 UTC（`timedatectl set-local-rtc 1` 的遗留配置），导致重启后时间错乱。
6. **证书本身过期**（不是时间问题，别误判）。

### 处置

```bash
# 1) 启用并校正时间（chrony 为例）
systemctl enable --now chronyd
chronyc makestep                       # 立即跳变校正（首次接入时用）
chronyc tracking                       # 确认 System time / Last offset 已经收敛

# 2) 确保硬件时钟用 UTC
timedatectl set-local-rtc 0
timedatectl set-ntp true

# 3) 放行 NTP（示例）
firewall-cmd --add-service=ntp --permanent && firewall-cmd --reload
# 或在安全组里放行出方向 UDP 123

# 4) 若确认是证书本身过期
#    换证 + 重启相关服务，而不是去改时间
openssl x509 -in cert.pem -noout -enddate
```

补充两点：

- 时间跳变会带来副作用：日志时间线错乱、`cron` 任务可能重复或跳过、数据库主从复制异常、集群选主抖动。所以**校时动作本身也要当作一次变更**来对待，别在数据库主库上随手 `makestep`。
- 时间同步正常**不代表**证书没问题。`sys.time_sync` 报 `已同步` 时，请回到"证书是否真的在有效期内、证书链是否完整、CA 是否受信任"这几条上继续查。

## 附：通用下钻工具箱

无论遇到哪种现象，这几条命令都值得先跑一遍。

| 命令 | 看什么 | 关键字段/输出 |
| --- | --- | --- |
| `vmstat 1 10` | CPU、内存、换页、IO、上下文切换全景 | `r`（就绪队列）、`b`（阻塞/D 状态）、`si`/`so`（换页，非零即异常）、`wa`（IO 等待） |
| `iostat -x 1 5` | 每块盘的繁忙度与延迟 | `%util`、`aqu-sz`（队列深度）、`await`、`r_await`/`w_await` |
| `free -m` | 内存水位 | **看 `available` 列**，不要只看 `used` |
| `dmesg -T \| tail -80` | 内核报错 | OOM、IO error、ext4/xfs 错误、网卡 down、SELinux AVC |
| `ss -s` / `ss -lntp` | 套接字总览 / 监听端口与进程 | 各状态计数、监听地址、对应 PID |
| `ps -eo state,pid,wchan:25,comm \| awk '$1=="D"'` | 卡在不可中断睡眠的进程 | 谁被 IO 卡住，`wchan` 显示内核等待点 |
| `pidstat -w -u -d 1 5` | 按进程看 CPU/IO/上下文切换 | 非自愿上下文切换（`cswch/s` vs `nvcswch/s`） |
| `top -o %CPU` / `top -o %MEM` | 实时进程排行 | 注意 `%wa` 与 `%st` 两行 |
| `cat /proc/pressure/{cpu,io,memory}` | 内核级资源压力（PSI） | `some` 与 `full` 的平均值，`full` 高说明整机被拖住 |
| `journalctl -p err --since '1 hour ago' --no-pager` | 近期错误日志 | 配合 `-u <unit>` 缩小范围 |
| `systemctl --failed --no-pager` | 失败的服务单元 | 与 `svc.failed.*` 对应 |
| `lsblk -o NAME,SIZE,TYPE,MOUNTPOINT,RO` | 块设备与挂载树 | 有没有 `RO` 标记、设备是否在线 |
| `lsof -nP +L1` | 已删除但被占用的文件 | 空间不释放的元凶 |
| `df -h; df -i` | 容量与 inode | **两条永远一起看** |

## 附：opsbox 明确不做的事

写在这里，是为了让你在它没报出问题时知道该往哪儿继续查，而不是误以为"全绿就没问题"。

| 不覆盖 | 说明 | 该用什么 |
| --- | --- | --- |
| **历史趋势与尖峰** | 它是一次性快照，看不到"昨天下午三点发生过什么" | `sar`、Prometheus + Grafana、`iostat`/`vmstat` 连续观测 |
| **容器 cgroup 限额** | 读的是主机 `/proc/meminfo`，不解析 `memory.max`、`cpu.max` | `/sys/fs/cgroup/*`、`systemd-cgtop`、`kubectl top` |
| **认证日志（默认）** | 默认不走 `auth.log`，且有 journald 时只用 `-p err`，看不到 info 级的认证失败 | `journalctl -u ssh`、`grep 'Failed password'`，或调整 `OB_CFG_LOG_FILES` |
| **磁盘配额** | 不检查 `quota`/`xfs_quota` | `repquota -a`、`xfs_quota -x -c 'report -h'` |
| **文件系统一致性** | 不检查元数据损坏、不做 `fsck` | `dmesg`、救援模式下 `fsck` |
| **硬件健康** | 不读 SMART/NVMe 健康日志 | `smartctl -a`、厂商带外管理 |
| **漏洞与合规** | 只覆盖少数几条"日常真会出事"的基线项，不是漏洞扫描器，也不替代 CIS Benchmark 工具 | 专业扫描器 + 配置管理平台 |
| **跨机关联** | 单机视角，看不到"整个集群都慢"这种系统性问题 | 集中式监控、链路追踪 |
| **业务语义** | 不解析业务日志含义，只做条数与模板聚类 | 应用自身的日志与 APM |
