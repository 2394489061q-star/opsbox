# opsbox 阈值说明

> 本文档解决什么问题：把 opsbox 每一个可调阈值摊开讲清楚——它叫什么、默认多少、用什么口径算出来、什么场景该动、动成多少合适。同时把四个最容易误解的统计口径单独讲透（内存使用率、负载倍数、网卡错误率、磁盘 IO 延迟），因为它们是这个项目与"随手敲命令"最大的区别所在。

---

## 一、阈值在哪里生效

所有阈值都是 `lib/core.sh` 中 `ob_conf_defaults()` 里的普通 shell 变量。加载顺序（后者覆盖前者）：

```
内置默认值 → /etc/opsbox/opsbox.conf → <安装目录>/conf/opsbox.conf
           → ~/.config/opsbox/opsbox.conf → --conf 指定的文件
```

**推荐做法**：不要改仓库里的 `conf/opsbox.conf`，把你实际要覆盖的项写进 `/etc/opsbox/opsbox.conf`，这样升级时不会被覆盖。改完立即生效，不需要重启服务。

三类配置项的优先级需要区分清楚：

| 类别 | 举例 | 谁覆盖谁 |
| --- | --- | --- |
| 命令行参数 | `-i 5`、`-m disk,memory` | **最高**。`-i` 在配置加载完成后还会再覆盖一次 `OB_CFG_SAMPLE_INTERVAL` |
| 配置文件 | `OB_CFG_DISK_WARN="75"` | 覆盖内置默认值，也会覆盖同名环境变量 |
| 环境变量 | `OPSBOX_SAMPLE_INTERVAL`、`OPSBOX_TOP_N`、`OPSBOX_PROC_ROOT` | 只作为**默认值的来源**，会被配置文件覆盖 |

注意命名差异：采集根路径的**环境变量**是 `OPSBOX_PROC_ROOT`，而**配置项**是 `OB_CFG_PROC_ROOT`。

另外有一组不在配置模板里、但代码确实支持的"命令覆盖"变量，用于注入假数据或在非标准环境里指定可执行文件：`OB_CMD_DF`、`OB_CMD_SYSTEMCTL`、`OB_CMD_JOURNALCTL`、`OB_CMD_TIMEDATECTL`、`OB_CMD_SS`。测试夹具就是靠它们工作的。

### 判定的两个基本规则

1. **`high` 与 `low` 两个方向**。绝大多数指标是"越大越糟"（`high`）：`值 ≥ crit` 判 CRIT，`值 ≥ warn` 判 WARN。少数是"越小越糟"（`low`）：`值 ≤ crit` 判 CRIT，`值 ≤ warn` 判 WARN。目前只有 `mem.available`（可用内存绝对余量）是 `low`。
2. **测不到 ≠ 没问题**。任何数值取不到、不是数字时，检查项产出的是 `UNKNOWN` 而不是静默通过。这是刻意的设计：`UNKNOWN` 会出现在报告和 `list` 里，提醒你"这项没查成"，而不是假装正常。

## 二、四个容易误解的口径

这四项是本项目的设计要点，也是最容易和"凭感觉判断"产生分歧的地方。

### 2.1 内存使用率用 `MemTotal - MemAvailable`，不是 `free` 的 used 列

```
内存使用率 = (MemTotal - MemAvailable) / MemTotal × 100%
```

数据源是 `/proc/meminfo`。为什么不用 `free -m` 的 `used` 列？

- `free` 的 `used` 列大致是 `MemTotal - MemFree - Buffers - Cached`，它把**可回收的 page cache 和可回收 slab** 当成"已用"，于是任何一台"读过大量文件"的机器都会显示 80%~95% 的占用——这是运维现场最经典的误判来源。
- `MemAvailable` 是内核给出的估算值：**在不触发 swap 的前提下，还能满足新应用内存需求的数量**，它已经扣掉了不可回收的部分、加回了可回收的部分。
- 两者在缓存型负载上的差距可以非常夸张：`free` 看着"快满了"，而 `MemAvailable` 显示还有一大半可用。

实测（`healthy` 测试夹具，`MemTotal=16384000 kB`、`MemAvailable=11264000 kB`）：opsbox 报 `mem.used = 31.00%`，而 `free` 的 used 口径会接近 60% 以上。

**什么时候该调**：如果你的业务**故意**大量使用 page cache 且希望更保守地预警，可以把 `OB_CFG_MEM_WARN/CRIT` 从 85/95 下调到 80/90；反过来，如果这台机器就是缓存型服务（CDN 节点、对象存储网关），可以放宽到 90/97。

`mem.used` 旁边还有两条互补的检查，配合起来看才完整：

- `mem.available`：可用内存的**绝对下限**（MB，`low` 方向）。百分比在 128G 的机器上会有欺骗性（85% 仍然剩 19G），绝对余量才反映"还能撑多久"。
- `mem.commit`：`Committed_AS / CommitLimit`，反映**内存超售**。它超过 100% 时，即使物理内存还有空余，`malloc` 也会失败。

### 2.2 负载阈值是「核数的倍数」，不是绝对值

`cpu.load1` 与 `cpu.load15` 用的不是绝对负载值，而是：

```
比值 = loadavg / 逻辑 CPU 核数
```

配置项是 `OB_CFG_LOAD_WARN_MULT`（默认 `1.0`）与 `OB_CFG_LOAD_CRIT_MULT`（默认 `2.0`）。含义是"负载达到核数的几倍"：

- `1.0` → 负载等于核数，队列开始出现等待 → WARN
- `2.0` → 平均每个核要处理两个任务 → CRIT

报告里的观测值会写成 `比值 0.10 (0.42/4)` 这种形式（比值、分子、分母一目了然）。**这样 4 核的机器和 64 核的机器可以共用同一份配置**，这也是它比"负载 > 5 就告警"更实用的原因。

核数的取值顺序：`/proc/cpuinfo` 中 `^processor` 的行数 → `/proc/stat` 中 `^cpuN` 的个数 → `nproc` → 兜底 `1`。

判定负载时必须和另外三项一起看，因为**运行队列里包含不可中断睡眠（D 状态）的进程**——磁盘卡住同样会把负载推高，而 CPU 其实很闲：

| 组合 | 指向 |
| --- | --- |
| 负载高 + `cpu.usage` 高 + `cpu.iowait` 低 | 真的是算力不足，考虑扩容或优化 |
| 负载高 + `cpu.usage` 低 + `cpu.iowait` 高 | 瓶颈在存储/网络存储，加 CPU 没用 |
| 负载高 + `mem.dirty` 上千 MB | 脏页回写跟不上，后端存储写不动 |
| 负载高 + `cpu.steal` 高 | 宿主机超卖，做什么优化都没用，应找云厂商 |

**什么时候该调**：专用数据库机希望更早发现排队，收到 `0.7 / 1.5`；混部机器或本身就跑批处理任务、负载经常在 2~3 倍的机器，放宽到 `2.0 / 4.0`。核数很少（1~2 核）的机器上，倍数阈值会非常敏感，建议收紧倍数但配合 `OB_CFG_DISABLE_CHECKS` 处理噪音。

### 2.3 网卡用错误率 / 丢包率，不用累计计数

```
错误率 = (rx_errs + tx_errs) / (rx_packets + tx_packets) × 100%
丢包率 = (rx_drop + tx_drop) / (rx_packets + tx_packets) × 100%
```

数据源是 `/proc/net/dev`，`lo` 回环接口被排除。

**为什么不用累计值**：`/proc/net/dev` 里给出的是**自开机以来的累计计数**。一台运行了一年的机器累计几万个 `errs` 可能完全无害；而一台刚启动十分钟的机器出现几百个 `errs` 才是真问题。累计值与运行时长强相关，用它做固定阈值必然误报。比率与运行时长无关，所以可以直接设一个固定阈值（默认 WARN `0.01%`、CRIT `0.1%`）。

**注意分母是包数，不是字节数**。一个 9000 字节的巨帧和一个 64 字节的小包在分母里权重相同，这对"链路层错误"这个语义是恰当的。

**什么时候该调**：物理机、直连交换机、对链路质量敏感的场景（存储网络、RDMA 前置网络）可以收紧到 `0.001 / 0.01`；虚拟化环境、容器节点、veth/网桥密集的宿主机上，少量丢包是常态，放宽到 `0.1 / 1` 更实际。

检查项 id 带接口名后缀，例如 `net.err_rate.eth0`、`net.drop_rate.enp0s3`，所以可以只静音某一块噪音网卡。

### 2.4 磁盘平均 IO 延迟 = `ms_io` 增量 / 完成 IO 次数增量

```
延迟(ms) = Δms_io / Δ(完成 IO 次数)
吞吐(MB/s) = Δsectors × 512 / 1048576 / 采样间隔
```

数据源是 `/proc/diskstats`，并且**只统计整盘**：先用 `/sys/block/*` 取出整盘设备名单，把分区排除掉，避免同一份 IO 被统计两遍。字段取法是：

| 代码里用的字段 | diskstats 中的位置 | 含义 |
| --- | --- | --- |
| `$4 + $8` | reads completed + writes completed | 完成的 IO 次数（分母） |
| `$6 + $10` | sectors read + sectors written | 扇区数，用于算吞吐 |
| `$13` | `ms_io`（io_ticks） | 设备"正在做 IO"的累计毫秒数 |

三次采样都要**取两次快照做差**，所以需要 `OB_CFG_SAMPLE_INTERVAL` 秒的等待；两次之间完成的 IO 次数为 0 时不做判定，显示为"窗口内无 IO 活动"。

**这个口径的准确含义，以及它和 `iostat` 的 `await` 的区别**：

- `Δms_io` 是**墙钟时间**——设备处于"有 IO 在进行"状态的总时长，不管当时有几个请求在排队。
- 因此当队列深度大于 1 时，`Δms_io` 会**小于**各请求各自耗时之和，这个比值约等于 `iostat` 的 `await` **除以平均队列深度**，可以理解为"单次 IO 延迟的下界估计"。
- 实践含义：**不要**在 `QD=32` 的高并发盘上把 opsbox 报出来的数字和 `iostat -x` 的 `await` 直接对比，两者不在同一个量纲上。opsbox 这个值回答的是"这块盘在采样窗口里平均忙多久完成一次 IO"，用于判断"存储是不是瓶颈"足够，用于精确刻画单请求延迟请用 `iostat`。

**什么时候该调**：

| 存储类型 | 建议 WARN / CRIT |
| --- | --- |
| 本地 NVMe | `5 / 20` |
| 云 SSD（默认） | `20 / 100` |
| 机械盘 / 大容量 SATA | `50 / 200` |
| 网络存储（NFS / Ceph / 云盘挂载） | `30 / 150`，同时把 `OB_CFG_IOWAIT_WARN/CRIT` 一起放宽 |

### 2.5 补充：`UNKNOWN` 不等于 OK

任何取不到的数值都会产出 `UNKNOWN`，并且**计数进 `OB_N_UNKNOWN`**。但在整体状态推导中，`UNKNOWN` 是兜底状态：

```
有 CRIT → CRIT ；否则有 WARN → WARN ；否则（有 UNKNOWN 且无任何 OK）→ UNKNOWN ；否则 OK
```

也就是说，一台机器上有两条检查是 `UNKNOWN`、其余都 `OK` 时，整体结论仍是 `OK`、退出码仍是 `0`。如果你需要"采集不到就告警"，请在 Prometheus 侧对 `opsbox_check_status == 3` 建规则，详见 [docs/监控接入.md](监控接入.md)。

## 三、逐模块阈值清单

下表中的"检查项 id"是 `opsbox list` 里真实出现的 id。带 `<slug>` 的表示按实例展开：挂载点 `/` → `root`、`/data` → `data`；网卡 `eth0` → `eth0`；systemd 单元 `nginx.service` → `nginx_service`（点会被换成下划线）。

### 3.1 通用项

| 配置项 | 默认值 | 含义 | 使用它的检查项 |
| --- | --- | --- | --- |
| `OB_CFG_ENABLED_MODULES` | `system cpu memory disk network service log security` | 默认运行的模块。`-m` 会**替换**它，不是追加 | 全部 |
| `OB_CFG_DISABLE_CHECKS` | 空 | 逗号分隔的静音列表，写法见第五节 | 全部 |
| `OB_CFG_SAMPLE_INTERVAL` | `1` | 采样间隔秒数，供 CPU 使用率与磁盘 IO 延迟做两次快照。`0` = 不等待 | `cpu.usage`、`cpu.iowait`、`cpu.steal`、`disk.io_latency`、`disk.io_throughput` |
| `OB_CFG_TOP_N` | `5` | Top N 列表长度 | `mem.top`、`log.biggest` |
| `OB_CFG_REPORT_TITLE` | `Linux 服务器巡检报告` | 报告标题（`md` 模式下的 H1） | 报告头部 |
| `OB_CFG_PROC_ROOT` | `/proc` | 采集根路径，可指向夹具 | 全部采集 |
| `OB_CFG_SYS_ROOT` | `/sys` | 同上 | 磁盘整盘名单、SELinux 状态 |
| `OB_CFG_ETC_ROOT` | `/etc` | 同上 | 安全模块、`os-release` |
| `OB_CFG_VAR_ROOT` | `/var` | 同上 | 日志文件扫描 |
| `OB_CFG_RUN_ROOT` | `/run` | 同上 | 待重启标记、容器判定、systemd 判定 |

### 3.2 `system` 模块（系统底座）

| 配置项 | 默认值 | 含义与口径 | 检查项 id | 什么时候调 / 调成多少 |
| --- | --- | --- | --- | --- |
| `OB_CFG_UPTIME_MIN_WARN` | `600` | 运行时长低于此值（秒）时提示"疑似刚重启"。只有 WARN，没有 CRIT | `sys.uptime` | 频繁滚动发布的机器可以调到 `300`；想更敏感地发现崩溃循环可以调到 `1800` |
| `OB_CFG_FD_WARN` / `OB_CFG_FD_CRIT` | `80` / `90` | 文件句柄使用率（%）。口径：`(allocated - unused) / max × 100`，来自 `/proc/sys/fs/file-nr` | `sys.fd_usage` | 高并发网关、Nginx、Java 应用节点收到 `70 / 85` 更稳妥 |
| `OB_CFG_PID_WARN` / `OB_CFG_PID_CRIT` | `80` / `95` | PID 用量（%）＝ 进程数 / `kernel.pid_max` | `sys.pid_usage` | 一般不用改。Fork 密集型服务（CGI、短任务队列）可收到 `70 / 90` |
| `OB_CFG_OOM_WARN` / `OB_CFG_OOM_CRIT` | `1` / `5` | 时间窗口内（`OB_CFG_LOG_SINCE`）内核 OOM 事件次数，匹配 `out of memory`、`oom-killer`、`killed process` | `sys.oom_events` | 内存紧张的机器希望"杀一次就要知道"，把 WARN 设为 `1` 即可（默认已是） |

无阈值配置项的检查：

| 检查项 id | 判定 | 说明 |
| --- | --- | --- |
| `sys.identity` | 恒 OK | 主机名 / 发行版 / 内核，只是信息项 |
| `sys.time_sync` | 已同步 → OK；未同步 → WARN；无法判定 → UNKNOWN | 依赖 `timedatectl show` 的 `NTPSynchronized`，退化到 `chronyc tracking` |
| `sys.reboot_required` | 存在标记 → WARN；容器 → UNKNOWN | 检查 `/run/reboot-required` 与 `/var/run/reboot-required` |
| `sys.kernel_swappiness` | `> 60` → WARN，否则 OK | **阈值硬编码 60，不可配** |
| `sys.kernel_overcommit` | `0`/`1` → OK；`2` → WARN | **硬编码**。`2`（禁止超售）会让内存紧张时分配直接失败 |

### 3.3 `cpu` 模块（CPU 与负载）

| 配置项 | 默认值 | 含义与口径 | 检查项 id | 什么时候调 / 调成多少 |
| --- | --- | --- | --- | --- |
| `OB_CFG_LOAD_WARN_MULT` / `OB_CFG_LOAD_CRIT_MULT` | `1.0` / `2.0` | **核数的倍数**，不是绝对值。见 2.2 节 | `cpu.load1`、`cpu.load15` | 数据库专用机 `0.7 / 1.5`；批处理/混部机 `2.0 / 4.0` |
| `OB_CFG_CPU_WARN` / `OB_CFG_CPU_CRIT` | `85` / `95` | CPU 使用率（%）＝ `(总增量 - idle增量) / 总增量 × 100`，两次采样做差 | `cpu.usage` | 长时间 85% 以上就该扩容了。稳态服务可收到 `70 / 85`；批处理机放宽到 `90 / 98` |
| `OB_CFG_IOWAIT_WARN` / `OB_CFG_IOWAIT_CRIT` | `10` / `25` | IO 等待占比（%），`/proc/stat` 第 5 列（iowait）增量占比 | `cpu.iowait` | 存储慢的机器建议收紧到 `5 / 15`（iowait 一高就说明该查盘）；本地 NVMe 机器可放宽 |
| `OB_CFG_CPU_STEAL_WARN` / `OB_CFG_CPU_STEAL_CRIT` | `5` / `15` | 被宿主机抢占的 CPU 占比（%），`/proc/stat` 第 9 列（steal）增量占比 | `cpu.steal` | 云主机上持续 > 5% 就该考虑提工单。裸金属通常恒 0，可静音 |

无阈值配置项的检查：

| 检查项 id | 判定 | 说明 |
| --- | --- | --- |
| `cpu.info` | 恒 OK | 核数 + CPU 型号 |
| `cpu.runqueue` | 运行队列 ≥ `2 × 核数` → WARN；≥ `4 × 核数` → CRIT | **阈值由核数推导，不可配**。取自 `/proc/loadavg` 第 4 字段的分子（`procs_running`） |
| `cpu.steal` 的判定门限 | steal ≤ `0.01%` 时直接判 OK，不参与阈值比较 | **硬编码**，避免裸金属上浮点噪声引发的噪音告警 |

### 3.4 `memory` 模块（内存与 Swap）

| 配置项 | 默认值 | 含义与口径 | 检查项 id | 什么时候调 / 调成多少 |
| --- | --- | --- | --- | --- |
| `OB_CFG_MEM_WARN` / `OB_CFG_MEM_CRIT` | `85` / `95` | 内存使用率（%）＝ `(MemTotal - MemAvailable) / MemTotal × 100`，见 2.1 节 | `mem.used` | 缓存型服务放宽到 `90 / 97`；关键业务机收到 `75 / 90` |
| `OB_CFG_MEMAVAIL_MIN_MB` / `OB_CFG_MEMAVAIL_CRIT_MB` | `256` / `64` | 可用内存的**绝对下限（MB）**。`low` 方向：≤ warn 判 WARN，≤ crit 判 CRIT | `mem.available` | 大内存机器建议提高余量：`1024 / 256`；容器节点可 `512 / 128` |
| `OB_CFG_SWAP_WARN` / `OB_CFG_SWAP_CRIT` | `50` / `80` | Swap 使用率（%） | `mem.swap` | 见下方"Swap 特别注意" |
| `OB_CFG_DIRTY_WARN_MB` / `OB_CFG_DIRTY_CRIT_MB` | `512` / `2048` | 脏页堆积（MB），`/proc/meminfo` 的 `Dirty` | `mem.dirty` | 写入密集的存储节点收到 `256 / 1024`；只读型节点可放宽 |
| `OB_CFG_COMMIT_WARN` / `OB_CFG_COMMIT_CRIT` | `90` / `100` | 内存承诺比（%）＝ `Committed_AS / CommitLimit × 100` | `mem.commit` | 跑大量 JVM/容器且开了 overcommit 的机器，收到 `85 / 95` 能更早预警"分配失败" |
| `OB_CFG_ZOMBIE_WARN` / `OB_CFG_ZOMBIE_CRIT` | `10` / `50` | 僵尸进程数量（个） | `mem.zombie` | 进程模型频繁 fork 的服务可放宽到 `50 / 200`；一般机器保持默认 |

**Swap 特别注意**：`mem.swap` 在 `SwapTotal = 0` 时**不看阈值**，直接给出 WARN「未启用 Swap」（理由：内存瞬时峰值时没有缓冲，会直接触发 OOM Killer）。**Kubernetes 节点通常明确禁用 Swap**，所以这不是故障，请在 `OB_CFG_DISABLE_CHECKS` 里加上 `mem.swap`，否则每个节点都会常驻一条 WARN。

无阈值配置项的检查：

| 检查项 id | 判定 | 说明 |
| --- | --- | --- |
| `mem.capacity` | 恒 OK | 总内存与可回收缓存量 |
| `mem.top` | 恒 OK | 内存占用 Top N（由 `OB_CFG_TOP_N` 控制条数），直接读 `/proc/<pid>/status` |

### 3.5 `disk` 模块（磁盘与 inode）

| 配置项 | 默认值 | 含义与口径 | 检查项 id | 什么时候调 / 调成多少 |
| --- | --- | --- | --- | --- |
| `OB_CFG_DISK_WARN` / `OB_CFG_DISK_CRIT` | `80` / `90` | 分区容量使用率（%），取自 `df -P -k` 的 Capacity 列 | `disk.usage.<slug>` | 日志/存储节点收到 `75 / 85`；业务盘按数据增速定，85% 一天涨 10% 比 95% 不动更危险 |
| `OB_CFG_INODE_WARN` / `OB_CFG_INODE_CRIT` | `80` / `90` | inode 使用率（%），取自 `df -P -k -i` | `disk.inode.<slug>` | 小文件海场景（邮件队列、session 文件、镜像层）收到 `70 / 85` |
| `OB_CFG_DISK_LAT_WARN` / `OB_CFG_DISK_LAT_CRIT` | `20` / `100` | 平均 IO 延迟（ms），口径见 2.4 节 | `disk.io_latency` | 本地 NVMe `5 / 20`；机械盘 `50 / 200`；网络存储 `30 / 150` |
| `OB_CFG_LOG_BIG_MB_WARN` / `OB_CFG_LOG_BIG_MB_CRIT` | `512` / `2048` | **单个日志文件体积（MB）**。注意它虽然叫 `LOG_`，但被 `disk` 模块的 `disk.big_log` 使用 | `disk.big_log` | 应用日志按天切割的机器可放宽；对有严格 logrotate 要求的机器收到 `100 / 500` |
| `OB_CFG_DISK_MIN_SIZE_MB` | `100` | 总容量小于此值（MB）的挂载点不参与容量检查 | 过滤规则 | 想连小分区一起盯就调小；噪音多就调大 |
| `OB_CFG_DISK_EXCLUDE_FS` | 见下方代码块 | 不参与检查的文件系统类型（正则，`\|` 分隔） | 过滤规则 | 新增了需要忽略的文件系统（如 `zfs`、`fuse.*`）时追加 |
| `OB_CFG_DISK_EXCLUDE_MNT` | `/run\|/dev\|/sys\|/proc\|/snap` | 不参与检查的挂载点前缀 | 过滤规则 | 挂载点数量多、只想盯关键分区时追加，例如加上 `\|/boot` |

`OB_CFG_DISK_EXCLUDE_FS` 的默认值（按原样列出）：

```
tmpfs|devtmpfs|squashfs|overlay|proc|sysfs|cgroup|cgroup2|autofs|debugfs|tracefs|ramfs|fusectl|mqueue|hugetlbfs|securityfs|pstore|configfs|bpf|binfmt_misc|nsfs
```

无阈值配置项的检查：

| 检查项 id | 判定 | 说明 |
| --- | --- | --- |
| `disk.readonly` | 有可疑只读挂载 → **CRIT**；读不到 `/proc/mounts` → UNKNOWN（无阈值可调） | 扫描 `/proc/mounts`，挑出 `opts` 含 `ro` 且文件系统与挂载点都不在排除规则内的挂载点。采集失败与"没有只读挂载"被刻意区分开 |
| `disk.detail.<slug>` | 恒 OK | 每个候选分区的容量明细（已用 / 可用 / 文件系统），方便事后复盘 |
| `disk.io_throughput` | 恒 OK | 采样窗口内的吞吐（MB/s），是 `disk.io_latency` 的配套信息项 |

> **`disk.readonly` 的已知噪音**：代码只按 `OB_CFG_DISK_EXCLUDE_FS` 与 `OB_CFG_DISK_EXCLUDE_MNT` 两套规则过滤，**并没有专门排除 `/boot`**。如果这台机器上本来就有正常挂载成只读的分区（例如某些发行版的 `/boot`、只读 bind mount），该项会误报 CRIT。处置办法是把挂载点加进 `OB_CFG_DISK_EXCLUDE_MNT`，或在 `OB_CFG_DISABLE_CHECKS` 里静音 `disk.readonly`。

### 3.6 `network` 模块（网络与连接）

| 配置项 | 默认值 | 含义与口径 | 检查项 id | 什么时候调 / 调成多少 |
| --- | --- | --- | --- | --- |
| `OB_CFG_TCP_WARN` / `OB_CFG_TCP_CRIT` | `5000` / `10000` | TCP 连接总数（条），统计 `/proc/net/tcp` 与 `tcp6` 的所有状态 | `net.tcp_total` | 网关、负载均衡、长连接服务按实际连接规模调，常见放到 `20000 / 50000` |
| `OB_CFG_TIMEWAIT_WARN` / `OB_CFG_TIMEWAIT_CRIT` | `3000` / `8000` | `TIME_WAIT` 连接数 | `net.timewait` | 短连接密集的 Web 前端可放宽到 `10000 / 30000`；**正解是应用侧连接池，而不是调小 `tcp_fin_timeout`** |
| `OB_CFG_CLOSEWAIT_WARN` / `OB_CFG_CLOSEWAIT_CRIT` | `500` / `2000` | `CLOSE_WAIT` 连接数 | `net.closewait` | 这一项通常应该**收紧**（如 `200 / 1000`），因为 CLOSE_WAIT 堆积是应用没 `close()` 的指纹，越早发现越好 |
| `OB_CFG_CONNTRACK_WARN` / `OB_CFG_CONNTRACK_CRIT` | `80` / `95` | conntrack 表使用率（%）＝ `nf_conntrack_count / nf_conntrack_max × 100` | `net.conntrack` | K8s 节点、NAT 网关、Docker 宿主机建议收到 `70 / 85`；不承担 NAT 的机器可直接静音 |
| `OB_CFG_IFACE_ERR_RATE_WARN` / `OB_CFG_IFACE_ERR_RATE_CRIT` | `0.01` / `0.1` | 接口**错误率**（%），口径见 2.3 节 | `net.err_rate.<iface>` | 物理网络收紧到 `0.001 / 0.01`；虚拟化环境放宽到 `0.1 / 1` |
| `OB_CFG_IFACE_DROP_RATE_WARN` / `OB_CFG_IFACE_DROP_RATE_CRIT` | `0.01` / `0.1` | 接口**丢包率**（%），口径见 2.3 节 | `net.drop_rate.<iface>` | 同上一行；突发流量大的机器若因网卡队列溢出误报，应先调 ring buffer 再放宽阈值 |

无阈值配置项的检查：

| 检查项 id | 判定 | 说明 |
| --- | --- | --- |
| `net.syn_recv` | `SYN_RECV > 50` → WARN，否则 OK | **阈值硬编码 50，不可配，且只有 WARN 没有 CRIT** |
| `net.sensitive_ports` | 见下 | **端口清单硬编码**：`3306 5432 6379 27017 9200 11211 2375 2379`，且只在监听地址为 `*:PORT`（全网暴露）时才 WARN |
| `net.default_route` | 无默认路由 → **CRIT** | 无阈值可调。缺少默认路由会让所有跨网段访问失败 |
| `net.traffic` | 恒 OK | 各接口累计流量与错误/丢包总数（信息项） |
| `net.listen_count` / `net.listen_ports` | 恒 OK | 监听端口数量与清单；优先用 `ss -H -lntu`，没有 `ss` 时退化解析 `/proc/net/tcp` |

### 3.7 `service` 模块（服务与进程）

| 配置项 | 默认值 | 含义 | 检查项 id | 什么时候调 |
| --- | --- | --- | --- | --- |
| `OB_CFG_REQUIRED_UNITS` | 空 | 逗号分隔的"必须 active"服务清单，非 active 直接 **CRIT** | `svc.required.<slug>` | 一上线就该填，例如 `sshd.service,nginx.service,docker.service`。留空表示不做强制检查 |
| `OB_CFG_OPTIONAL_UNITS` | 空 | 逗号分隔的"建议 active"服务清单，非 active 只给 **WARN** | `svc.optional.<slug>` | 填辅助服务，例如 `chronyd.service,crond.service` |

无阈值配置项的检查：

| 检查项 id | 判定 | 说明 |
| --- | --- | --- |
| `svc.systemd` | 有 `systemctl` → OK；容器内或没有 → UNKNOWN | 没有 `systemctl` 时模块会跳过后续服务检查 |
| `svc.failed.<slug>` | 每个失败单元一条，恒 **CRIT** | 只报数量没有意义，所以拆成"哪一个单元挂了"。id 里 `.` 会变成 `_`，如 `nginx.service` → `svc.failed.nginx_service` |
| `svc.failed` | 无失败单元时输出一条 OK | |
| `svc.proc_total` | 进程数 > 0 → OK；枚举不到任何进程（`OB_CFG_PROC_ROOT` 不可读）→ UNKNOWN | 进程总数 |
| `svc.run_queue` | 恒 OK | 可运行进程 / 总进程（内核口径），取自 `/proc/loadavg` 第 4 字段 |

### 3.8 `log` 模块（日志与崩溃）

| 配置项 | 默认值 | 含义与口径 | 检查项 id | 什么时候调 / 调成多少 |
| --- | --- | --- | --- | --- |
| `OB_CFG_LOG_SINCE` | `1 hour ago` | journalctl 的时间窗口。**同时影响 `sys.oom_events`** | `log.errors`、`sys.oom_events` | 想覆盖完整一天，设为 `24 hours ago`；只想看最近，用 `15 min ago` |
| `OB_CFG_LOG_ERR_WARN` / `OB_CFG_LOG_ERR_CRIT` | `50` / `500` | 窗口内的错误日志条数 | `log.errors` | 噪音大的老系统放宽到 `200 / 2000`；关键系统收到 `10 / 100` |
| `OB_CFG_LOG_FILES` | `/var/log/syslog /var/log/messages /var/log/kern.log` | **没有 journald 时**才使用的日志文件清单（空格分隔） | 数据源 | 想把 SSH 爆破纳入扫描，追加 `/var/log/auth.log`（Debian 系）或 `/var/log/secure`（RHEL 系） |
| `OB_CFG_LOG_SCAN_BYTES` | `2097152`（2 MiB） | 每个日志文件扫描的**尾部字节数**；也是 OOM 检测退化到 `/var/log/messages` 时读取的长度 | 数据源 | 日志量大、错误稀疏时调大（如 `10485760`），代价是变慢 |
| `OB_CFG_LOG_BIG_MB_WARN` / `OB_CFG_LOG_BIG_MB_CRIT` | `512` / `2048` | 单个日志文件体积阈值（MB）。供 `disk` 模块的 `disk.big_log` 使用 | `disk.big_log` | 见 3.5 节 |
| `OB_CFG_CRASH_DUMP_DIRS` | `/var/crash /var/spool/abrt` | 崩溃转储目录（空格分隔） | `log.crash_dumps` | 按发行版调整；容器里通常没有，会得到 `0 个` |
| `OB_CFG_CRASH_WARN` / `OB_CFG_CRASH_CRIT` | `1` / `5` | 崩溃转储数量（个） | `log.crash_dumps` | 想"出现一次 core 就要知道"，WARN 设为 `1`（默认已是）。注意数量为 `0` 时直接判 OK，不参与阈值比较；而 `OB_CFG_CRASH_DUMP_DIRS` 里的目录**全都不存在**时给 UNKNOWN——这是刻意区分"没有崩溃"与"查不到" |

无阈值配置项的检查：

| 检查项 id | 判定 | 说明 |
| --- | --- | --- |
| `log.source` | 恒 OK | 数据源来自 journald 还是传统日志文件；**没有任何可读日志源时不会输出这一条** |
| `log.top1` / `log.top2` / `log.top3` | 恒 OK | 错误日志聚类 Top 3。做法是把消息里的十六进制串、数字归一化成 `HEX` / `N` 后统计词频，所以"300 条错误里 287 条是同一个 message"能被直接看出来 |
| `log.biggest` | 恒 OK | 体积最大的 Top N 日志文件（信息项，不做判定） |

> **日志模块的取数优先级**：优先 `journalctl -p err --since <窗口>`；取不到内容时才退化到扫描 `OB_CFG_LOG_FILES` 的文件尾部。这意味着**在有 journald 的机器上，`Failed password` 这类认证失败记录默认看不到**——它们是 info 级，不会进入 `-p err` 窗口。要借助日志聚类观察 SSH 爆破，请手工执行 `journalctl -u ssh -u sshd --since '1 hour ago'`，或按 [docs/故障排查手册.md](故障排查手册.md) 里的方法处理。

### 3.9 `security` 模块（安全基线）

| 配置项 | 默认值 | 含义 | 检查项 id | 什么时候调 |
| --- | --- | --- | --- | --- |
| `OB_CFG_SSHD_WEAK_PERMITROOT` | `1` | `PermitRootLogin yes` 时的定性：`1` → **CRIT**，`0` → **WARN** | `sec.ssh_permitroot` | 已经用密钥 + 来源白名单做了补偿控制，可设为 `0` 降级 |
| `OB_CFG_SEC_SUID_ENABLE` | `0` | 是否启用 SUID/SGID 扫描。**默认关闭**（全盘扫描慢，且基线需要人工维护） | `sec.suid` | 需要时设为 `1` |
| `OB_CFG_SEC_SUID_ROOT` | `/usr/bin` | SUID 扫描的根目录（只在 `ENABLE=1` 时生效） | `sec.suid` | 想覆盖全盘就设为 `/`（会很慢，注意 `find -xdev` 不跨文件系统） |
| `OB_CFG_SEC_SUID_MAX` | `500` | SUID/SGID 文件数量的 WARN 阈值 | `sec.suid` | 按你自己的基线快照定；**CRIT 阈值固定为它的 2 倍，不可单独配置** |

无阈值配置项的检查：

| 检查项 id | 判定 | 说明 |
| --- | --- | --- |
| `sec.uid0` | 除 `root` 外存在 UID 0 账户 → **CRIT** | 读 `/etc/passwd` |
| `sec.empty_passwd` | `/etc/shadow` 中存在空密码字段 → **CRIT** | 非 root 运行时读不到 shadow，会给 UNKNOWN（正常现象） |
| `sec.ssh_passwordauth` | `PermitRootLogin`/`PasswordAuthentication` 判定见表下 | 读 `sshd_config`，取不到时按 UNKNOWN / OK 分别处理 |
| `sec.ssh_permitroot` | `yes` → 按 `OB_CFG_SSHD_WEAK_PERMITROOT` 判 CRIT 或 WARN；`"" / no / prohibit-password / without-password / forced-commands-only` → OK；其他取值 → WARN | |
| `sec.ssh_port` | 恒 OK | 显示 SSH 监听端口 |
| `sec.firewall` | `active`/`running` → OK；`inactive`/`stopped`/`empty` → WARN；检测不到 → UNKNOWN；容器 → UNKNOWN | 依次探测 `ufw`、`firewall-cmd`、`nft`、`iptables` |
| `sec.mac` | SELinux enforcing / AppArmor present → OK；permissive → WARN；都没有 → WARN | |
| `sec.ip_forward` | `= 1` → WARN；`= 0` → OK | K8s 节点 / NAT 网关 / Docker 宿主机上这是正常的，请静音 `sec.ip_forward` |

> **`sshd_config` 取值的已知偏差**：采集函数对同一个配置键取的是**文件中最后一次出现的值**（逐行覆盖）。而 `sshd` 自身的行为是**首次出现的值生效**。所以当 `sshd_config` 里同一个键写了多次（例如主配置写了 `PermitRootLogin no`，末尾的 `Include` 或追加片段又写了 `yes`）时，opsbox 的判断可能与 sshd 的实际行为相反。模块给出的建议文案本身提醒了"sshd 以首次出现的值为准"，遇到这种配置请手工确认。另外，`Include`/`Match` 引入的文件不会被解析。

### 3.10 已定义但当前未接入任何检查项的配置

以下配置项在 `lib/core.sh` 里有默认值，但**没有任何模块读取它们**。写进配置文件不会报错，也不会有任何效果——如果你在别处看到这些名字，不要以为它们能起作用：

| 配置项 | 默认值 | 状态 |
| --- | --- | --- |
| `OB_CFG_FAILED_UNIT_WARN` / `OB_CFG_FAILED_UNIT_CRIT` | `1` / `3` | **未接入**。`svc.failed.<unit>` 对每个失败单元恒判 CRIT，不按失败数量分级 |
| `OB_CFG_PASSWD_MAX_AGE` | `90` | **未接入**。没有任何检查项统计密码有效期 |
| `OB_CFG_LOG_TAIL_LINES` | `200` | **未接入**。日志条数与 Top N 都不使用它 |

### 3.11 硬编码阈值汇总

这些判定写死在模块里，改不了；如需绕过，只能用 `OB_CFG_DISABLE_CHECKS` 静音整个检查项：

| 检查项 id | 硬编码判定 |
| --- | --- |
| `cpu.runqueue` | WARN = `2 × 核数`，CRIT = `4 × 核数` |
| `cpu.steal` | steal ≤ `0.01%` 时不判定，直接 OK |
| `sys.kernel_swappiness` | `> 60` → WARN |
| `sys.kernel_overcommit` | `= 2` → WARN |
| `net.syn_recv` | `> 50` → WARN（只有 WARN） |
| `net.sensitive_ports` | 端口清单 `3306 5432 6379 27017 9200 11211 2375 2379` |
| `sec.suid` | CRIT = `OB_CFG_SEC_SUID_MAX × 2` |
| `disk.readonly` | 命中即 CRIT |
| `net.default_route` | 缺失即 CRIT |
| `svc.failed.<unit>` | 命中即 CRIT |
| `svc.required.<unit>` | 非 active 即 CRIT |
| `svc.optional.<unit>` | 非 active 即 WARN |
| `mem.swap`（SwapTotal = 0） | 直接 WARN，不看阈值 |

## 四、不同角色机器的推荐配置

以下都是可以直接追加到 `/etc/opsbox/opsbox.conf` 的片段。**建议先按默认值跑一到两周，用真实数据校准之后再收紧**——一上来就调到很敏感，只会让你很快开始忽略告警。

### 4.1 数据库机（MySQL / PostgreSQL / Redis / MongoDB）

关注点：延迟抖动、Swap、脏页、内存余量。

```bash
# /etc/opsbox/opsbox.conf —— 数据库机

# 专用机，负载排队要早发现
OB_CFG_LOAD_WARN_MULT="0.7"
OB_CFG_LOAD_CRIT_MULT="1.5"

# 存储是命门，单次 IO 延迟收紧（本地 NVMe 用 5/20；云 SSD 用 10/50）
OB_CFG_DISK_LAT_WARN="10"
OB_CFG_DISK_LAT_CRIT="50"

# iowait 一高就该查盘
OB_CFG_IOWAIT_WARN="5"
OB_CFG_IOWAIT_CRIT="15"

# 内存留足余量：百分比 + 绝对余量双保险
OB_CFG_MEM_WARN="80"
OB_CFG_MEM_CRIT="90"
OB_CFG_MEMAVAIL_MIN_MB="2048"
OB_CFG_MEMAVAIL_CRIT_MB="512"

# 换页对数据库是灾难，Swap 阈值收紧
OB_CFG_SWAP_WARN="10"
OB_CFG_SWAP_CRIT="30"

# 脏页堆积意味着刷盘跟不上
OB_CFG_DIRTY_WARN_MB="256"
OB_CFG_DIRTY_CRIT_MB="1024"
```

数据库机上 `sys.kernel_swappiness` 应当是 1~10，`mem.commit` 建议收到 `85 / 95`（JVM/连接池会大量预留地址空间）。如果这台机器不承担转发，`sec.ip_forward` 和 `sec.firewall`（有云安全组时）可以静音。

### 4.2 Web 前端机（Nginx / 应用服务）

关注点：磁盘增长、连接状态、日志体积。

```bash
# /etc/opsbox/opsbox.conf —— Web 前端机

# 日志增长快，容量要早预警
OB_CFG_DISK_WARN="75"
OB_CFG_DISK_CRIT="85"

# 单文件日志不该长这么大，logrotate 没配好就是问题
OB_CFG_LOG_BIG_MB_WARN="128"
OB_CFG_LOG_BIG_MB_CRIT="512"

# 高并发短连接是常态，放宽 TIME_WAIT 与总数
OB_CFG_TCP_WARN="20000"
OB_CFG_TCP_CRIT="50000"
OB_CFG_TIMEWAIT_WARN="10000"
OB_CFG_TIMEWAIT_CRIT="30000"

# CLOSE_WAIT 是应用没 close() 的指纹，必须收紧
OB_CFG_CLOSEWAIT_WARN="200"
OB_CFG_CLOSEWAIT_CRIT="1000"

# 静态文件多，inode 也是真实风险
OB_CFG_INODE_WARN="70"
OB_CFG_INODE_CRIT="85"

# 声明必须活着的服务
OB_CFG_REQUIRED_UNITS="sshd.service,nginx.service"
```

Web 前端机的 `mem.used` 通常不高（进程模型轻），`mem.swap` 与 `mem.zombie` 用默认值即可。如果应用是 PHP/Python 这类短生命周期模型，`sys.pid_usage` 可以收到 `70 / 90`。

### 4.3 Kubernetes 节点

关注点：conntrack、转发、Swap 的"正常异常"。

```bash
# /etc/opsbox/opsbox.conf —— K8s 节点（含 Docker 宿主机）

# conntrack 是 K8s 节点最真实的容量瓶颈之一
OB_CFG_CONNTRACK_WARN="70"
OB_CFG_CONNTRACK_CRIT="85"

# 节点上连接数天然很高
OB_CFG_TCP_WARN="30000"
OB_CFG_TCP_CRIT="80000"

# 这些在本角色上是"设计如此"，不是故障，必须静音
# mem.swap  : K8s 官方建议禁用 Swap，不静音会常驻 WARN
# sec.ip_forward : kube-proxy / CNI 必须开启转发
# sec.firewall   : 策略由 NetworkPolicy / 安全组统一管理
# disk.readonly  : 若节点上有只读 bind mount，避免误报
OB_CFG_DISABLE_CHECKS="mem.swap,sec.ip_forward,sec.firewall"
```

补充两点：

- 容器里跑 opsbox 时，`disk.io_latency`、`svc.systemd`、`sec.firewall` 等会自然变成 `UNKNOWN`（采集不到宿主信息），这属于预期；要看节点真实状态请在**宿主机**上运行。
- 节点上 `mem.dirty` 通常比普通机器高，若经常触发 WARN，先确认是正常的批量落盘还是存储瓶颈，再决定是否放宽到 `1024 / 4096`。

### 4.4 日志 / 存储节点（ELK、对象存储、备份机、NAS 前端）

关注点：容量与 inode 水位、大文件、机械盘的延迟预期。

```bash
# /etc/opsbox/opsbox.conf —— 日志/存储节点

# 存储型节点必须更早预警，因为清理/扩容都要时间
OB_CFG_DISK_WARN="75"
OB_CFG_DISK_CRIT="85"

# 小文件海是这类节点的典型故障
OB_CFG_INODE_WARN="70"
OB_CFG_INODE_CRIT="85"

# 机械盘 / 大容量 SATA：延迟预期本来就高，避免噪音
OB_CFG_DISK_LAT_WARN="50"
OB_CFG_DISK_LAT_CRIT="200"

# 大日志文件是业务特征，不是异常
OB_CFG_LOG_BIG_MB_WARN="4096"
OB_CFG_LOG_BIG_MB_CRIT="16384"

# 写入密集，脏页堆积的阈值可以略放宽（但仍然要盯）
OB_CFG_DIRTY_WARN_MB="1024"
OB_CFG_DIRTY_CRIT_MB="4096"

# 单节点容量大，绝对余量要给足
OB_CFG_MEMAVAIL_MIN_MB="2048"
OB_CFG_MEMAVAIL_CRIT_MB="512"
```

这类节点还建议：把 `OB_CFG_DISK_MIN_SIZE_MB` 调大（例如 `1024`）以过滤掉一堆小分区；如果挂了大量数据盘导致报告很长，用 `OB_CFG_DISABLE_CHECKS` 只保留关键分区（见下一节）。

## 五、用 `OB_CFG_DISABLE_CHECKS` 精确静音

### 5.1 先拿到准确的 id

```bash
./opsbox list
```

`list` 会先真正跑一遍采集，然后输出四列：**状态 / 检查项 ID / 说明 / 观测值 | 阈值**。请从这一列里**原样复制** id——带实例后缀的项（挂载点、网卡、systemd 单元）必须连后缀一起写。

常见 id 形态：

| 形态 | 例子 | 说明 |
| --- | --- | --- |
| 模块前缀 + 名称 | `mem.used`、`disk.readonly`、`net.conntrack` | 大多数检查项 |
| 带挂载点后缀 | `disk.usage.root`、`disk.usage.data`、`disk.inode.root`、`disk.detail.data` | 后缀来自 `ob_slug`：`/` → `root`，`/var/lib/docker` → `var_lib_docker` |
| 带网卡后缀 | `net.err_rate.eth0`、`net.drop_rate.enp0s3` | 原样使用接口名 |
| 带单元后缀 | `svc.failed.nginx_service`、`svc.required.sshd_service` | `.` 会被替换成 `_` |
| 系列聚合项 | `disk.usage`、`disk.inode` | 当某个系列一条实例都没采到时，会以不带后缀的形式产出 UNKNOWN |

### 5.2 写法与匹配规则

```bash
# /etc/opsbox/opsbox.conf
OB_CFG_DISABLE_CHECKS="disk.inode.root,net.conntrack,mem.swap,sec.firewall"
```

匹配规则（按实现如实说明）：

- 以**逗号分隔**，两端与内部的**空格会被自动忽略**，所以 `"a, b"` 与 `"a,b"` 等价。
- 每一项必须是**完整 id**，**不支持通配符、不支持前缀匹配**。写 `disk.inode` 不会静音 `disk.inode.root`。
- 每一项会同时与两种形式比较：`<裸 id>`（如 `mem.used`）和 `<模块名>.<id>`（如 `memory.mem.used`）。**推荐总是写裸 id**，它更短、更贴近 `opsbox list` 的输出。
- 匹配失败不会有任何提示——静音是静默的。写完请用 `opsbox list` 复核一下那一项是不是真的消失了。

### 5.3 静音的真实效果

被静音的检查项会在写进结果集**之前**就被丢弃，因此它**既不进入报告，也不计入 `OK/WARN/CRIT/UNKNOWN` 任何一个计数**，自然也不影响退出码与 `opsbox_overall_status`。

这个语义带来两个实践结论：

- 静音是"从结果里拿掉"，而不是"标记为已忽略"。事后看报告时无法区分"这项没问题"和"这项被静音了"，所以**建议在配置文件里用注释记录每一处静音的原因和日期**：
  ```bash
  # 2024-05-12 静音：节点本来就没有 Swap（K8s 官方建议）
  # 2024-06-03 静音：本机挂了 12 块数据盘，只保留根分区告警
  OB_CFG_DISABLE_CHECKS="mem.swap,sec.ip_forward,disk.usage.data,disk.inode.data"
  ```
- 如果只是想"降低敏感度"，优先调阈值；只有在该项对本机**语义上不适用**时才静音。

### 5.4 常见静音场景速查

| 场景 | 建议静音 | 原因 |
| --- | --- | --- |
| K8s 节点 / 禁用了 Swap | `mem.swap` | 不静音会常驻 WARN |
| K8s 节点 / Docker 宿主机 | `sec.ip_forward` | 转发是必需能力 |
| 有云安全组，主机无防火墙 | `sec.firewall` | 边界防护在安全组层 |
| 不承担 NAT 转发 | `net.conntrack` | 该表基本用不到 |
| 裸金属 / 物理机 | `cpu.steal` | 无 steal 指标，会长期 UNKNOWN |
| 大量数据盘，只想盯根分区 | `disk.usage.data,disk.inode.data`（按实际挂载点） | 报告过长会淹没重点 |
| 容器内运行 | `svc.systemd`、`disk.io_latency`、`sec.firewall` | 采集不到宿主信息，长驻 UNKNOWN |
| 系统本来就有只读挂载 | `disk.readonly` | 见 3.5 节的已知噪音说明 |
