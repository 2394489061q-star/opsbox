# opsbox 监控接入

> 本文档解决什么问题：把 opsbox 的一次性巡检变成持续监控。包含 Prometheus（node_exporter textfile collector）的完整落地步骤与可直接使用的告警规则、Zabbix 的两种接入方式、Nagios/Icinga 插件包装、定时巡检 + 邮件/Webhook 告警的最小实现，以及 CI 里 `--fail-on` 的用法。阈值本身的含义见 [docs/阈值说明.md](阈值说明.md)。

---

## 一、Prometheus：用 node_exporter textfile collector 落地

这是最省事也最稳的一条路：opsbox 把自己的一次巡检结果渲染成 Prometheus 文本格式，落成一个 `.prom` 文件，node_exporter 的 textfile collector 在每次被抓取时读它并以本机指标暴露出去。

链路：

```
cron ──► opsbox check -f prom ──► /var/lib/node_exporter/textfile_collector/opsbox.prom
                                            │
                                   node_exporter（每次 /metrics 抓取时读取）
                                            │
                                       Prometheus ──► Alertmanager
```

### 1.1 完整落地步骤

**第一步：确认 node_exporter 的 textfile 目录**

textfile collector 默认是启用的，但**必须显式指定目录**。检查启动参数：

```bash
ps -o args= -C node_exporter
# 期望看到：--collector.textfile.directory=/var/lib/node_exporter/textfile_collector
```

如果没有这个参数，请在 systemd unit（通常是 `/etc/systemd/system/node_exporter.service`）的 `ExecStart` 上补上，然后 `systemctl daemon-reload && systemctl restart node_exporter`。

```bash
mkdir -p /var/lib/node_exporter/textfile_collector
```

**第二步：先手工验证一次输出**

```bash
/opt/opsbox/opsbox check -q --fail-on never -f prom \
  -o /var/lib/node_exporter/textfile_collector/opsbox.prom
head -n 20 /var/lib/node_exporter/textfile_collector/opsbox.prom
```

确认文件名**以 `.prom` 结尾**——node_exporter 只读取该后缀的文件，其它后缀会被直接忽略。

**第三步：挂上定时任务**

```bash
# /etc/cron.d/opsbox-prom
# 每 5 分钟刷新一次巡检结果。先写临时文件再 mv，避免 node_exporter 读到半个文件。
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
*/5 * * * * root /opt/opsbox/opsbox check -q --fail-on never -f prom \
  -o /var/lib/node_exporter/textfile_collector/opsbox.prom.tmp \
  && mv /var/lib/node_exporter/textfile_collector/opsbox.prom.tmp \
        /var/lib/node_exporter/textfile_collector/opsbox.prom
```

三处细节：

| 细节 | 为什么 |
| --- | --- |
| 先写 `.tmp` 再 `mv` | `opsbox -o` 是直接打开目标文件写入，不是原子操作。node_exporter 恰好在这一刻抓取就会读到截断的文件，导致 `node_textfile_scrape_error 1` 或指标缺失。`.tmp` 后缀不会被 node_exporter 读取，`mv` 在同目录内是原子操作 |
| `--fail-on never` | 监控场景下状态由指标表达，退出码没有任何消费者；若用默认的 `warn`，cron 会因为退出码非零而持续给 root 发邮件 |
| `PATH=...` | cron 的 PATH 很短，`ip`、`ss` 找不到会让相关检查项变成 `UNKNOWN`，凭空制造噪音 |

**第四步：权限**

文件由 root 创建，默认 umask 下是 `0644`，node_exporter 以非 root 运行时通常仍可读。如果你们的 node_exporter 目录权限收得很紧（例如 `0750` 且属主是 `prometheus`），需要显式处理：

```bash
# 方案 A：让文件对所有人可读
install -d -m 0755 /var/lib/node_exporter/textfile_collector

# 方案 B：把目录属组设为 node_exporter 的运行组，并让文件继承
chgrp node_exporter /var/lib/node_exporter/textfile_collector
chmod 0775 /var/lib/node_exporter/textfile_collector
```

**第五步：验证 node_exporter 真的读到了**

textfile collector 会为每个文件暴露一个 mtime 指标，这是最直接的验证方式：

```bash
curl -s http://localhost:9100/metrics | grep -E 'node_textfile_mtime_seconds|node_textfile_scrape_error'
# node_textfile_mtime_seconds{file="opsbox.prom"} 1.7e+09
# node_textfile_scrape_error 0
```

`node_textfile_scrape_error 0` 表示文件格式合法、没有解析错误；`mtime` 的时间戳应该和刚才 cron 跑的时间对得上。如果文件根本没被列出来，先检查后缀是不是 `.prom`、目录参数是否配错、以及 node_exporter 有没有读权限。

然后在 Prometheus 侧确认目标已被抓取：

```promql
opsbox_overall_status
```

### 1.2 opsbox 导出的全部指标

`-f prom` 的输出**只有下面 6 个指标**，每个都带 `# HELP` 与 `# TYPE` 注释：

| 指标名 | 类型 | 标签 | 含义 | 取值 |
| --- | --- | --- | --- | --- |
| `opsbox_check_status` | gauge | `module`、`check` | 单个检查项的状态 | `0`=OK、`1`=WARN、`2`=CRIT、`3`=UNKNOWN |
| `opsbox_check_total` | gauge | `status` | 本次巡检各状态的检查项**数量** | 标签取值 `ok`、`warn`、`crit`、`unknown`（小写） |
| `opsbox_overall_status` | gauge | 无 | 本次巡检的**整体**状态 | `0`=OK、`1`=WARN、`2`=CRIT、`3`=UNKNOWN |
| `opsbox_last_run_timestamp_seconds` | gauge | 无 | 本次巡检的完成时间（Unix 时间戳） | 秒 |
| `opsbox_run_duration_seconds` | gauge | 无 | 本次巡检耗时 | 秒 |
| `opsbox_info` | gauge | `hostname`、`os`、`kernel`、`version` | 巡检目标信息 | 恒为 `1` |

关于 `check` 标签的取值，有几点必须知道：

- 它**就是检查项的 id**。带实例后缀的项会展开成多条时间序列，例如：
  ```
  opsbox_check_status{module="disk",check="disk.usage.root"} 0
  opsbox_check_status{module="disk",check="disk.usage.data"} 0
  opsbox_check_status{module="network",check="net.err_rate.eth0"} 0
  opsbox_check_status{module="service",check="svc.required.nginx_service"} 0
  ```
- 因此标签基数取决于你这台机器上有多少挂载点、网卡和 systemd 单元，一般几十到上百条，完全可控。
- **恒为 `OK` 的信息项也会产生序列**（如 `cpu.info`、`mem.capacity`、`mem.top`、`disk.detail.*`、`net.listen_ports`、`log.top1`、`log.biggest`）。它们的值永远是 `0`，不要用"全量"规则去告警，否则时间序列和告警规则都会被这些噪音填满。

**为什么必须有 `opsbox_last_run_timestamp_seconds`**：textfile 里的内容是"上一次写入的结果"。如果 opsbox 本身挂了、cron 没跑、或者机器上 `/opt/opsbox` 被删了，**旧的 `.prom` 文件仍然留在磁盘上，指标会一直停留在最后一次的结果**——从 Prometheus 的角度看，一切正常。只有对时间戳做陈旧检测，才能发现"巡检已经不再执行"这件事。这是 textfile collector 这种接入方式最容易踩的坑。

### 1.3 可用的告警规则示例

下面这份规则可以直接放进 Prometheus 的 `rules/opsbox.yml`。请把抓取间隔（`scrape_interval`）与这里的 `for` 时长一起考虑：**`for` 至少应是抓取间隔的 2 倍**，否则一次瞬时抖动就会触发告警。

```yaml
groups:
  - name: opsbox
    rules:
      # ---- 整体状态 ----

      # 存在 CRIT：任何一项严重问题都会把整体状态推到 2
      - alert: OpsboxCrit
        expr: opsbox_overall_status >= 2
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.instance }} 巡检发现严重问题"
          description: >-
            存在 CRIT 检查项。在目标机上执行 `opsbox list`，
            state 列为 CRIT 的行即为问题项；也可用 `opsbox_check_status == 2` 在 Prometheus 里反查。

      # 存在 WARN：长期挂着的 WARN 也需要有人处理，否则会被彻底忽略
      - alert: OpsboxWarn
        expr: opsbox_overall_status == 1
        for: 6h
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.instance }} 巡检存在长期未处理的 WARN"

      # ---- 巡检自身是否还活着 ----

      # 超过 30 分钟没有新的巡检结果：cron 挂了、opsbox 被删了、或者机器时间异常
      - alert: OpsboxStale
        expr: time() - opsbox_last_run_timestamp_seconds > 1800
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.instance }} opsbox 巡检结果已过期"
          description: "最后一次成功巡检在 30 分钟前。请检查 cron 是否还在跑、textfile 目录是否被清理。"

      # 巡检耗时异常增长：说明某个采集环节变慢（例如 /proc 遍历变慢、df 卡住）
      - alert: OpsboxSlow
        expr: opsbox_run_duration_seconds > 60
        for: 15m
        labels:
          severity: info
        annotations:
          summary: "{{ $labels.instance }} opsbox 巡检耗时 {{ $value }}s"

      # ---- 采集失败 ----

      # UNKNOWN 表示"这项没查成"。注意它不会影响 opsbox 的退出码，
      # 想要"采集不到就告警"必须靠这条规则。
      - alert: OpsboxCheckUnknown
        expr: opsbox_check_status == 3
        for: 1h
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.instance }} 检查项 {{ $labels.check }} 无法采集"
          description: "该指标长时间无法判定，通常意味着采集路径不可读、命令缺失或运行在容器里。"

      # ---- 按检查项精确告警（推荐做法）----

      # 只读文件系统：文件系统自我保护或硬件/云盘故障，通常伴随数据风险
      - alert: OpsboxReadOnlyFilesystem
        expr: opsbox_check_status{check="disk.readonly"} >= 2
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.instance }} 出现只读挂载"
          description: "立即执行 `dmesg -T | tail -50` 查看 IO 报错，并优先做数据备份，不要着急 remount,rw。"

      # 分区容量：任意挂载点达到 CRIT
      - alert: OpsboxDiskUsageHigh
        expr: opsbox_check_status{check=~"disk\\.usage\\..+"} >= 2
        for: 10m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.instance }} 分区容量告急（{{ $labels.check }}）"

      # inode 耗尽：df -h 看着有空间却写不进去的经典原因
      - alert: OpsboxInodeHigh
        expr: opsbox_check_status{check=~"disk\\.inode\\..+"} >= 1
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.instance }} inode 使用率偏高（{{ $labels.check }}）"

      # 磁盘 IO 延迟：存储是常见瓶颈，单独给高优先级
      - alert: OpsboxDiskLatency
        expr: opsbox_check_status{check="disk.io_latency"} >= 2
        for: 15m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.instance }} 磁盘平均 IO 延迟过高"

      # 内存：区分"使用率高"和"可用余量低"两个不同信号
      - alert: OpsboxMemoryHigh
        expr: opsbox_check_status{check="mem.used"} >= 1
        for: 15m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.instance }} 内存使用率偏高"

      - alert: OpsboxMemoryLow
        expr: opsbox_check_status{check="mem.available"} >= 1
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.instance }} 可用内存余量不足"
          description: "随时可能触发 OOM Killer，请立即确认是否有进程异常膨胀。"

      # Swap 换页会造成数量级延迟抖动，比"内存占用高"更该被重视
      - alert: OpsboxSwapUsage
        expr: opsbox_check_status{check="mem.swap"} >= 2
        for: 15m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.instance }} Swap 使用率过高"

      # OOM：内核已经杀过进程，属于必须介入的事件
      - alert: OpsboxOomEvent
        expr: opsbox_check_status{check="sys.oom_events"} >= 1
        for: 0m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.instance }} 近期发生过 OOM"

      # conntrack 表：满了会直接丢新连接，现象是"能 ping 通但连不上"
      - alert: OpsboxConntrackHigh
        expr: opsbox_check_status{check="net.conntrack"} >= 1
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.instance }} conntrack 表使用率偏高"

      # CLOSE_WAIT 堆积是应用层未 close() 的指纹，值得单独告警
      - alert: OpsboxCloseWaitHigh
        expr: opsbox_check_status{check="net.closewait"} >= 1
        for: 15m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.instance }} CLOSE_WAIT 连接堆积"

      # 链路质量：错误率/丢包率非零就该看交换机端口
      - alert: OpsboxNicErrors
        expr: opsbox_check_status{check=~"net\\.(err_rate|drop_rate)\\..+"} >= 1
        for: 15m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.instance }} 网卡错误/丢包（{{ $labels.check }}）"

      # 服务失败：每一个失败单元都是一条独立序列
      - alert: OpsboxServiceFailed
        expr: opsbox_check_status{check=~"svc\\.failed\\..+"} >= 2
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.instance }} 服务单元失败（{{ $labels.check }}）"

      # 安全基线：非 root 的 UID 0 账户、空密码、SSH 允许 root 登录
      - alert: OpsboxSecurityBaseline
        expr: opsbox_check_status{module="security"} >= 2
        for: 30m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.instance }} 安全基线不通过（{{ $labels.check }}）"
```

几点使用建议：

- **`check=~"disk\\.usage\\..+"` 这类正则里必须写双反斜杠**，因为正则中的 `.` 需要转义成字面量点号；在 YAML 双引号字符串里 `\\` 表示一个 `\`，最终传给 PromQL 的是 `"disk\.usage\..+"`。
- 不要把 `opsbox_check_status >= 1` 当作一条通用告警。像 `sec.ssh_passwordauth`、`sec.mac`、`mem.swap` 这类项在很多环境里是长期 WARN（甚至是设计如此），全量规则会让你在一天之内就把所有 opsbox 告警静音掉。
- `OpsboxStale` 是这套规则里**最重要的一条**，因为其余规则全都建立在"文件是新鲜的"这个前提上。
- 如果同一个 Prometheus 抓很多台机器，`instance` 标签已经能区分来源；`opsbox_info` 的 `hostname` 标签适合在 Grafana 的表格面板里做展示。

## 二、Zabbix

两种方式各有适用场景：**UserParameter（被动/主动检查）** 适合 agent 已经在跑的标准环境；**trapper** 适合 agent 不方便执行长命令、或想把巡检集中到一台跳板机上跑的场景。

### 2.1 方式一：UserParameter

在 agent 侧新增一个配置文件：

```bash
# /etc/zabbix/zabbix_agentd.d/opsbox.conf
# 数字型：整体状态 0=OK 1=WARN 2=CRIT 3=UNKNOWN
UserParameter=opsbox.overall,/opt/opsbox/opsbox check -q --fail-on never -f prom 2>/dev/null | awk '/^opsbox_overall_status /{print $2}'

# 数字型：CRIT 检查项数量
UserParameter=opsbox.crit,/opt/opsbox/opsbox check -q --fail-on never -f prom 2>/dev/null | awk -F'[{} ]' '/^opsbox_check_total\{status="crit"\}/{print $NF}'

# 文本型：单行摘要，适合放在触发器描述或仪表盘里
UserParameter=opsbox.oneline,/opt/opsbox/opsbox check -q --fail-on never -f oneline 2>/dev/null

# 文本型：某一项的具体状态（把 check 名换成你关心的）
UserParameter=opsbox.check[*],/opt/opsbox/opsbox check -q --fail-on never -f prom 2>/dev/null | awk -v c="$1" '$0 ~ "^opsbox_check_status\\{.*check=\"" c "\"\\}" {print $NF}'
```

然后：

```bash
systemctl restart zabbix-agent     # 或 zabbix-agent2
zabbix_get -s 127.0.0.1 -k opsbox.overall
```

**三个必须注意的点：**

| 问题 | 说明 |
| --- | --- |
| **执行超时** | Zabbix agent 的 `Timeout` 参数默认只有 3 秒，而 opsbox 默认采样间隔就会 sleep 两次（CPU + 磁盘，约 2 秒），加上采集时间很容易超时。解决办法：**在 UserParameter 里加 `-i 0`**，或者把 agent 的 `Timeout` 调大（新版 Zabbix 支持到 30 秒，配置在 `zabbix_agentd.conf` 与 server 侧都要改） |
| **输出必须单行** | Zabbix 只取命令输出的第一行。`oneline` 格式天生满足；若用 `text` 或 `md` 会得到残缺内容 |
| **命令长度限制** | `UserParameter` 在旧版有 512 字符的长度限制，上面的命令都在安全范围内。用脚本文件包装（`UserParameter=opsbox.overall,/opt/opsbox/bin/zabbix-opsbox.sh`）可以彻底规避 |

对应的触发器表达式：

```
# 有 CRIT
{Template Opsbox:opsbox.overall.last()}>=2

# 采集失败（整体 UNKNOWN，通常是工具或权限问题）
{Template Opsbox:opsbox.overall.last()}=3

# 数据陈旧：超过 30 分钟没有更新（配合 zabbix 的 nodata 函数）
nodata(/Host/opsbox.overall,1800)=1
```

### 2.2 方式二：trapper（用 zabbix_sender 推送）

适合"巡检集中在一台机器上跑、结果推给 Zabbix"的模式。先在 Zabbix 上为每个指标建 **Zabbix trapper** 类型的 item（键名与下面一致，类型选"字符"或"数字"），再定时执行：

```bash
#!/usr/bin/env bash
# /opt/opsbox/bin/zabbix-push.sh
set -u
ZABBIX_SERVER="${1:-127.0.0.1}"
PROM="$(/opt/opsbox/opsbox check -q --fail-on never -f prom 2>/dev/null)"
HOSTNAME_FQDN="$(hostname -f 2>/dev/null || hostname)"

overall="$(printf '%s\n' "$PROM" | awk '/^opsbox_overall_status /{print $2}')"
crit="$(printf '%s\n' "$PROM"    | awk -F'[{} ]' '/^opsbox_check_total\{status="crit"\}/{print $NF}')"
warn="$(printf '%s\n' "$PROM"    | awk -F'[{} ]' '/^opsbox_check_total\{status="warn"\}/{print $NF}')"
unk="$(printf '%s\n' "$PROM"     | awk -F'[{} ]' '/^opsbox_check_total\{status="unknown"\}/{print $NF}')"
ts="$(printf '%s\n' "$PROM"      | awk '/^opsbox_last_run_timestamp_seconds /{print $2}')"

zabbix_sender -z "$ZABBIX_SERVER" -s "$HOSTNAME_FQDN" \
    -k opsbox.overall  -o "${overall:-3}" \
    -k opsbox.crit     -o "${crit:-0}" \
    -k opsbox.warn     -o "${warn:-0}" \
    -k opsbox.unknown  -o "${unk:-0}" \
    -k opsbox.last_run -o "${ts:-0}"
```

```bash
# /etc/cron.d/opsbox-zabbix
*/5 * * * * root /opt/opsbox/bin/zabbix-push.sh 10.0.0.5 >/dev/null 2>&1
```

trapper 方式的优点是不受 agent `Timeout` 限制、也不需要在每台机器上装 agent 侧脚本；缺点是"谁在什么时候推过"完全依赖 cron 的可靠性，所以**一定要给 trapper item 配上 `nodata()` 触发器**，否则推送断了你也不会知道。

## 三、Nagios / Icinga

opsbox 的退出码和 Nagios 插件契约**前三个值完全一致**，只有 3 和 4 的含义不同：

| 退出码 | opsbox 含义 | Nagios 含义 |
| --- | --- | --- |
| `0` | 全部通过 | OK |
| `1` | 存在 WARN | WARNING |
| `2` | 存在 CRIT | CRITICAL |
| `3` | **用法错误** | UNKNOWN |
| `4` | **采集失败** | （不存在，需要映射到 UNKNOWN） |

所以只需要一层薄包装把 3 和 4 都映射成 3。**注意包装脚本里不要加 `--fail-on never`**——那样退出码会恒为 0，分级信息就丢了；用默认的 `--fail-on warn` 正好对齐 Nagios 的三级语义。

```bash
#!/usr/bin/env bash
# /usr/lib/nagios/plugins/check_opsbox
# 用法：check_opsbox [额外传给 opsbox 的参数...]
set -u

OPSBOX=/opt/opsbox/opsbox

# oneline 的格式：<状态> <主机名>: <结论> | OK=n WARN=n CRIT=n UNKNOWN=n | <时间>
out="$("$OPSBOX" check -q -f oneline "$@" 2>/dev/null)"
rc=$?

# 只取竖线之前的正文作为插件输出，避免监控系统把其后的统计当成 performance data
summary="${out%%|*}"

case "$rc" in
    0|1|2)
        printf '%s\n' "$summary"
        exit "$rc"
        ;;
    3)
        printf 'UNKNOWN - opsbox 用法错误（rc=3）：%s\n' "$summary"
        exit 3
        ;;
    4)
        printf 'UNKNOWN - opsbox 采集失败（rc=4）：%s\n' "$summary"
        exit 3
        ;;
    *)
        printf 'UNKNOWN - opsbox 非预期退出码 rc=%s\n' "$rc"
        exit 3
        ;;
esac
```

三个实践提醒：

- 巡检一次默认要几秒（两次采样各 sleep 1 秒），Nagios 的 `check_timeout` 默认 60 秒足够；但如果你把 `OB_CFG_SAMPLE_INTERVAL` 调大到 30 秒，记得同步调大超时。
- 监控系统通常会保留最近一次的插件输出，`oneline` 里的计数（`OK=n WARN=n …`）对事后判断"是刚出的问题还是老问题"很有用。
- 如果同一台机器既要被 Nagios 检查又要写 textfile，建议两份都留：Nagios 看实时退出码，Prometheus 看趋势。

## 四、定时巡检 + 邮件 / Webhook 告警的最小实现

### 4.1 核心思路

不需要额外的框架，就是三件事：

1. cron 定时跑一次 opsbox，把 Markdown 报告落盘（留档 + 当邮件正文）；
2. 用**退出码**决定要不要打扰人；
3. 用**上次状态文件**做最基本的去重，避免同一问题每 5 分钟发一次邮件。

```bash
#!/usr/bin/env bash
# /opt/opsbox/bin/opsbox-alert.sh
set -u

OPSBOX=/opt/opsbox/opsbox
LOGDIR=/var/log/opsbox
STATEDIR=/var/lib/opsbox
MAILTO="ops@example.com"
WEBHOOK=""                      # 例如 https://hook.example.com/opsbox，留空则不发

mkdir -p "$LOGDIR" "$STATEDIR"

DAY="$(date +%F)"
report="$LOGDIR/opsbox-$DAY.md"
statefile="$STATEDIR/last-status"
host="$(hostname)"

# 1) 跑一次巡检并落盘 Markdown
"$OPSBOX" check -q --fail-on warn -f md -o "$report"
rc=$?

# 2) 把退出码翻译成一个粗粒度状态标签
case "$rc" in
    0) level="OK" ;;
    1) level="WARN" ;;
    2) level="CRIT" ;;
    *) level="TOOLERROR" ;;
esac

# 3) 读上次状态，做最简单的"状态变化才通知"
last=""
[ -r "$statefile" ] && last="$(cat "$statefile")"

# 4) OK 时清掉状态文件直接退出，不打扰任何人
if [ "$level" = "OK" ]; then
    printf 'OK\n' > "$statefile"
    exit 0
fi

# 5) 与上次状态相同则静默（每天最多重复提醒一次）
if [ "$level" = "$last" ] && [ -z "$(find "$statefile" -mmin +1440 2>/dev/null)" ]; then
    exit 0
fi

# 6) 工具自身异常（rc=3/4）必须发信，且内容要和业务问题区分开
if [ "$level" = "TOOLERROR" ]; then
    {
        printf 'opsbox 自身执行异常，退出码 %s。\n' "$rc"
        printf '退出码含义：3=用法错误 4=采集失败。\n'
        printf '常见原因：配置文件不可读、-o 的输出目录不存在、模块加载失败。\n'
    } | mail -s "[opsbox][$host] 巡检执行失败（rc=$rc）" "$MAILTO"
    printf '%s\n' "$level" > "$statefile"
    exit "$rc"
fi

# 7) 业务异常：发报告正文
mail -s "[opsbox][$host] $level - 巡检发现异常" "$MAILTO" < "$report"
printf '%s\n' "$level" > "$statefile"

# 8) Webhook（失败不影响退出码）
if [ -n "$WEBHOOK" ]; then
    curl -sS -m 10 -X POST -H 'Content-Type: application/json' \
        -d "{\"host\":\"$host\",\"level\":\"$level\",\"exit_code\":$rc,\"report\":\"$report\",\"ts\":$(date +%s)}" \
        "$WEBHOOK" >/dev/null 2>&1 || true
fi

exit "$rc"
```


### 4.2 关于"跑两次"的取舍

`opsbox` 一次运行只能产一种格式。如果你想让邮件主题是 `oneline`、正文是 `md`，就得跑两次——代价是采集做两遍、采样多等两轮，而且两次结果理论上可能有微小差异（例如磁盘又涨了 0.1%）。

三种选择：

| 方案 | 做法 | 适合 |
| --- | --- | --- |
| 只跑一次 md | 主题里用主机名 + 退出码 + 日期（如 `[opsbox][web-01] CRIT (rc=2) 2024-05-12`） | 推荐，绝大多数场景够用 |
| 跑两次 | 先用 `-f oneline` 拿主题，再用 `-f md` 拿正文 | 对邮件主题格式有硬要求时 |
| 只跑一次 json | 用 `jq` 从 `summary` 里取字段拼主题与正文 | 已有 `jq` 且想自己排版 |

### 4.3 Webhook 侧的建议

- **一定要设超时**（`curl -m 10`）并吞掉失败（`|| true`），否则一个挂掉的 webhook 会把整条巡检链路拖死；
- payload 里带上**退出码和级别**，接收端才能区分"业务问题"与"工具故障"；
- 把报告文件的**路径**发过去而不是正文全文，接收端按需拉取，能避免消息体过大；
- 如果用的是企业微信/钉钉/飞书这类机器人，注意它们的 JSON 结构与频率限制，建议在接收端做一次转换。

## 五、CI 集成：`--fail-on` 的用法

`--fail-on` 决定"多严重才让流水线红"。完整真值表（也见 [docs/快速开始.md](快速开始.md)）：

| 最坏状态 | `--fail-on ok` | `--fail-on warn`（默认） | `--fail-on crit` | `--fail-on never` |
| --- | --- | --- | --- | --- |
| `OK` | `0` | `0` | `0` | `0` |
| `WARN` | `1` | `1` | `0` | `0` |
| `CRIT` | `2` | `2` | `2` | `0` |
| `UNKNOWN` | `4` | `0` | `0` | `0` |

在 CI 里选哪个：

| 目的 | 选择 | 理由 |
| --- | --- | --- |
| 构建镜像前做一次硬性基线检查 | `--fail-on ok` | 任何 WARN 都不放过，适合安全基线（UID 0 账户、空密码、SSH 配置）这类"零容忍"项 |
| 只拦严重问题 | `--fail-on crit`（**最常用**） | 一条历史遗留的 WARN 不该让每次构建都红 |
| 只采集不判定 | `--fail-on never` | 结果只作为产物归档或喂给别的系统 |

### GitHub Actions

```yaml
- name: opsbox 基线巡检
  run: |
    chmod +x opsbox
    set +e
    ./opsbox check -m system,disk,memory,security \
      --fail-on crit -f md -o opsbox-report.md
    rc=$?
    set -e
    echo "opsbox 退出码：$rc"          # 3=用法错误 4=采集失败，需要和真实问题区分
    if [ "$rc" -ge 3 ]; then
      echo "::error::opsbox 自身执行失败（rc=$rc），请检查配置与运行环境"
      exit 1
    fi
    exit "$rc"

- name: 上传巡检报告
  if: always()
  uses: actions/upload-artifact@v4
  with:
    name: opsbox-report
    path: opsbox-report.md
```

### GitLab CI

```yaml
opsbox-check:
  stage: test
  script:
    - chmod +x opsbox
    - ./opsbox check -m system,disk,memory,security --fail-on crit -f json -o opsbox-report.json
  artifacts:
    when: always
    paths:
      - opsbox-report.json
```

### CI 里的三个注意点

1. **用 `-m` 限定模块**。构建容器里通常没有 systemd、没有 journald、看不到宿主磁盘，全量运行会得到一片 `UNKNOWN`。限定到 `system,disk,memory,security` 这类不依赖服务的模块，结论才有意义。
2. **把 `3` 和 `4` 与业务问题分开**。流水线只关心"非零"很容易把"工具没跑起来"误认为"机器有问题"，反过来更危险的是把"工具没跑起来"当成"一切正常"。上面两个示例都显式打印了退出码。
3. **注意容器环境下的判定差异**。以容器方式运行 `opsbox` 时，`svc.systemd`、`sec.firewall`、`disk.io_latency` 等会自然变成 `UNKNOWN`，这是预期行为，不要当成回归失败。
